# 检查点失败后插回没有回滚：排查与修复方案

日期：2026-10-15。起因：商店版 Pro 实盘验收（store-pro 分支 `docs/testing/2026-10-15-商店版Pro实盘验收.md` 第 3、4 节）。所有者同意后已按方案一和方案二 A 实现，见文末“实现与验证”。

## 结论

1. **插回后没回滚、脏标记没释放，是因为写入记录整个没了**，不是恢复逻辑漏了这种情况。（更正：后来查明删容器的是腾讯柠檬清理。TestFlight 版 12:02 进废纸篓后，它弹出“废纸篓残留”提示，12:55:43 在那个弹窗里点了清理，它删了 23 项并清空废纸篓。所以不是系统自己删的；只用访达清空废纸篓会不会删容器还没验证。下面写的“系统删掉”都按这个更正理解。）12:55:44 清空废纸篓（里面是 12:02 移进去的 TestFlight 版，和本地测试包同一个标识符 `top.qisw.volisle.mas`），系统在同一秒删掉了这个标识符的应用容器和扩展容器。写入记录就存在扩展容器里（`~/Library/Containers/top.qisw.volisle.mas.filesystem/…/VolisleWriteJournal`），正在进行的写入会话的记录跟着被删了。插回时扩展拿到的是 12:59:15 新建的空容器，恢复函数找不到任何记录，按“没有中断”处理，预检看到脏标记，只读挂载。
2. **12:56:03 的“检查点失败”大概率也是这个原因，不是硬盘在准备睡眠。** 记录目录被删后，下一次有新写入的检查点要在这个目录里新建批次文件，系统返回“无此文件或目录”，检查点失败。同一时段内核没有任何磁盘 I/O 错误。也就是说，Pro 验收里“睡眠前推出不可靠”的结论证据不足，要在没有这个干扰的情况下重测。
3. **卸载一直返回 EIO**：会话失败后，每次同步都返回 EIO；内核卸载时先同步，同步失败就放弃卸载，所以 `diskutil unmount` 永远失败，只能拔线。这是设计上的取舍（不让失败被当成成功），代价是失败后卷卸不下来。
4. 镜像上已复现第 1、2 点（用和扩展相同的写入日志源码）。恢复逻辑本身在“保留窗口已清空后检查点失败”时是正常的：四种故障注入都能回滚并释放脏标记。

### 代码位置

- 恢复找不到记录时静默返回：`apps/extension/Sources/WriteJournalRecovery.swift:142`（没有会话记录也没有结束记录 → `.none`），`NTFSVolume.swift:1524` 对 `.none` 不写日志。其余所有分支都有日志，这次一条都没有，说明走的就是这里。

## 镜像复现

写入日志驱动（`scripts/fixtures/write_journal_driver.swift`）加一个场景 `idle-fail`：会话写入并检查点 → 把时钟拨过保留窗口、清掉全部保留批次 → 再做一次修改 → 按参数注入故障并做检查点 → `nk_umount` → 停止会话（相当于拔线）→ 下次连接恢复。补丁见文末附录，编译方式同 `scripts/test-write-journal.py` 的 `build()`。

| 注入 | 检查点 | 卸载 | 下次连接 | 卷标志 |
|---|---|---|---|---|
| 设备刷新失败 `flush-fail` | 失败 | -1 | recovered | 干净 |
| 设备写失败 `fail` | 失败 | -1 | recovered | 干净 |
| 读原内容失败 `read-fail` | 失败 | -1 | recovered | 干净 |
| 无故障 `none`（只是没正常结束） | 成功 | 0 | recovered | 干净 |
| **记录目录被删 `dir-gone`** | **失败** | **-1** | **none** | **0x0001（脏）** |

最后一行和实盘现象完全一致。

## 修复方案

### 一、记录目录丢了要发现并就地重建（两个版本都用，必做）

写入日志存放位置不变，在会话里加一道检查：

1. `WriteJournalStore` 记下打开时目录的设备号和 inode，提供“目录是否还在原处”的检查：按路径 `stat` 失败，或 inode 和手里的句柄不一致（被删或被挪走，例如移进废纸篓），就算丢了。不能用链接数判断：APFS 上删掉的目录句柄链接数是 2，不是 0。
2. 检查放在 `checkpointJournal` 开头（250 ms 的定时器空闲时也会跑），以及 `flushGroup` 新建批次文件之前。
3. 发现丢了就在原路径重建：建目录 → 用**同一把密钥**写 `key.bin`（开着的批次文件的校验链才对得上）→ 加锁 → 存会话记录（状态 active，会话号和开始时的卷信息都不变）→ 如果有开着的批次文件，从旧句柄把内容整个拷到新目录、换成新句柄。保留窗口里已检查点的批次文件已经关了、找不回来，从保留列表里去掉，记一条日志说明“最近约 20 秒的拔线保护随记录一起丢失”。只回滚最新的一段仍然安全（回到这一段开始时的检查点）。
4. 重建失败才停止会话（和现在一样），并告诉应用（见三）。
5. 需要改动：`WriteJournalSession.store` 从 `let` 改为可替换，加一个由协调器调用的 `rehome`；`WriteJournalStore` 加一个“用给定密钥初始化空目录”的构造。改动集中在 `WriteJournal.swift`、`WriteJournalStore.swift`、`WriteJournalRecovery.swift`，`NTFSVolume.swift` 只在 `checkpointJournal` 里调一下，同时要换掉 `journalLock`。

效果：今天这种情况，清空废纸篓后 250 ms 内记录就重建好了，推出时检查点照常成功；即使之后拔线，下次连接也能回滚并释放脏标记。

注意：如果扩展**没在运行**时容器被删（比如拔线后、插回前删了应用副本），记录还是会丢，插回只能只读等检查。这种情况要么接受，要么做方案三。

### 二、会话失败后让卷能正常卸下（需要所有者定）

会话失败后，从上一个检查点之后的写入都会在下次连接时退回，不管是拔线还是卸载，丢的都一样；一直报 EIO 并不能多保住什么，只是逼用户拔线。可选：

- **A（推荐）**：失败后**第一次**同步照常报 EIO（让推出的那一方知道出错了），之后同步返回成功；所有修改操作仍然返回 EIO，`deactivate` 仍然报失败，记录保留，下次连接回滚。效果：第一次推出失败，再推一次就能卸下，不用拔线，也不是强制卸载。代价：失败后第二次起的同步不再报错，如果某个程序在失败前写了东西、之后才 fsync，它会以为写成功了（实际下次连接会被退回）。要配合三里的提示。
- **B**：保持现状（失败后卸不下，只能拔线），只在应用里明确提示“写入出错，请直接拔下，下次连接会自动退回最近的写入”。最保守，有了方案一后记录不会再丢，拔线是安全的。

A 需要在镜像上确认两件事：同步放行后内核确实完成卸载；`deactivate` 报错不会让设备一直被占着（如果会，参照激活被拒的做法，交还错误后结束这个扩展实例）。

### 三、让应用知道“写入已经失败”（建议做）

商店版：会话失败（以及方案一重建记录目录）时写一条 `StoreMountStatus` 状态，应用在菜单栏和主窗口提示，而不是只显示“推出失败”。官网版：后台组件和应用如何拿到这个状态要另外看（本次没有查）。

### 不推荐现在做：把记录挪到应用组容器（方案三）

应用组容器这次没被删，挪过去可以连“扩展不在运行时删了应用副本”也防住。但要迁移旧记录、官网版扩展要加应用组权限、商店版要过审核的权限说明，代价大，收益只在很少见的情况。先做一、三。

## 对其他事项的影响

- **Pro“睡眠前推出”**：这次失败的直接原因是记录目录被删，不能据此断定推出和硬盘睡眠准备冲突。电源日志里硬盘驱动“SetState 用了 3.4 秒”是它正常的睡眠准备，内核没有报 I/O 错误。建议在排除这个干扰后重测一次再决定去留。
- **希捷 2T 现状**：带着本机加的脏标记，但对应的记录已经不在了，商店版只能只读挂载。按原计划接 Windows 检查，或者用官网版“在 Mac 上检查”。数据核对过（`big.bin` 完整）。

- 以后测试时不要在盘屿读写挂载期间清空装着同标识符副本的废纸篓；换装测试包前先卸下盘。

## 实现与验证（2026-10-15，方案一 + 方案二 A）

所有者同意方案一，方案二选 A。方案三（应用提示）没做。

### 改了什么

- `WriteJournalStore`：记下打开时目录的设备号和 inode；`isInPlace` 按路径 `lstat` 比对，不一致就算目录被删或被挪走。
- `WriteJournalSession.rehome()`：只在没有开着的批次文件时调用。按原路径重建目录（连上级一起建），在新目录里加锁并存会话记录；丢掉随旧目录一起没了的保留批次，也丢掉还没接管的“接续会话”交接；记一条错误日志。调用点有三个：
  - `flushGroup` 要新建批次文件之前；
  - `checkpoint` 没有批次可关时；
  - `checkpoint` 刚关完一个批次时。这一批记在旧目录里，设备刷新已经做完。
- `recordsMissing`：`checkpointJournal` 把它当作检查点到期的条件。250 ms 定时器在空闲时也会马上重建，所以今天那种“空闲 45 分钟后拔线”也能恢复。
- 可安全拔下的判断（`durability`）：随旧目录丢掉的批次，在它原本的保留窗口到期前不报“已持久”。不然应用会提前提示可以拔线，而硬盘缓存里可能还有这部分没写进盘。这一条是审查时发现后补上的。
- `WriteJournalCoordinator.finish` 不再接收外面新开的记录目录，改用会话自己当前的目录，先做检查点（需要时会重建），并关掉重建时拿的锁。
- `NTFSVolume.synchronize`：会话失败后，第一次同步照常报 EIO，之后的同步放行，内核就能完成卸载；`deactivate` 仍然报失败。检查点失败的日志里现在会带上错误原因。

### 验证

- 写入日志驱动加了 `records-gone` 场景，`scripts/test-write-journal.py` 加了 7 项检查，`--quick` 也会跑：
  - 目录被删、被挪走，各自覆盖空闲时、有新修改、有开着的批次三种时机，之后都拔线。结果都能回滚，卷干净，新会话能开。被丢掉的批次在窗口到期前不报“可拔”，到期后报。
  - 原路径被占用、无法重建：会话停止，修改全部被拒绝，和修复前一样只能等检查。
- 修复前同样的场景是 none + 脏标记（见上文复现表）。
- 完整矩阵 1468 项全部通过（arm64）。这一轮跑的代码还没加“可拔判断”那一条，加上后只重跑了 `--quick`：10 项，arm64 和 x86_64 都通过，原有的“可拔”报告用例也在其中。

**测试开关**：构建时设 `VOLISLE_TEST_CHECKPOINT_FAIL=1`（`scripts/build-fskit-extension.sh`，构建记录里写 `test_checkpoint_fail`），在卷上新建名为 `volisle-test-fail-next-checkpoint` 的文件后，下一次检查点失败（停止会话，与设备出错时走同一条路）。`build-store-package.sh` 和 `release.sh` 见到这个环境变量直接拒绝，商店包还会再查一次构建记录；两处都已实测会拒绝。

#### 方案二 A：通过

| 步骤 | 结果 |
|---|---|
| 写入基线，静置 45 秒（超过 20 秒保留窗口），再写一批，紧接着建触发文件 | 约 1 秒后日志“检查点失败（测试开关）”；之后写入返回 EIO |
| 第一轮：`diskutil unmount` 两次 | 第一次失败（日志“写入会话已失败：本次同步报错；之后的同步放行”），第二次成功 |
| 第二轮：直接 `hdiutil detach`（不加 force）两次 | 第一次“资源忙”，第二次推出成功 |
| `deactivate` | 报错（预期），系统另记一条 `failed to unregister fd with kernel`；出错的扩展实例随后退出，没有占着设备，推出不受影响 |
| 重挂 | “上次写入中断已回滚到最后一致点并释放本机脏标记”，读写挂载；基线逐文件校验一致，失败前没检查点的那批和触发文件都被退回 |

注意：失败后会退回到保留窗口之前的检查点，所以失败前约 20 秒内的写入都会退回（第一轮基线只静置了 3 秒，整批被退回，符合设计）。唯一的那次 EIO 可能被系统每 30 秒一次的同步先用掉，之后第一次卸载就会成功（第三轮实测如此）。

#### 删除容器的方式

- **访达清空废纸篓不会删容器**：15:33:58 用访达清空（里面有同标识符副本），应用容器和扩展容器的创建时间都没变，containermanagerd 没报 stale entry，写入照常。删容器的只是柠檬清理。

- **把应用扔进废纸篓再装回，系统设置里的扩展开关会被重置为关闭**（`mount -F` 查询显示 disabled），与柠檬无关；要所有者重新打开。
- 柠檬三次清理（15:36:41、15:38:29、15:42:51）都删掉了应用容器和扩展容器，应用组容器 `6N5T3G6H33.top.qisw.volisle.mas`（创建于 10-11）三次都还在。

### 方案二 A 的已知代价

失败后第一个到来的同步不一定是应用自己的 fsync，可能是每 30 秒一次的系统同步。之后应用再 fsync 会得到成功，但失败前没做检查点的那部分写入，下次连接时会被退回。官网版的后台组件和应用也只会看到“推出成功”。要让用户知道写入出过错，得做方案三（应用提示）。

## 方案三：商店版写入记录改放应用组容器（2026-10-15 晚，所有者同意）

- **商店版**：写入记录放在应用组容器 `~/Library/Group Containers/6N5T3G6H33.top.qisw.volisle.mas/VolisleWriteJournal`。商店版扩展本来就有这个应用组的权限，签名和权限都不用改。应用组容器在两次柠檬清理后都还在。
- **官网版**：位置不变，仍在扩展自己的容器里。
- **升级兼容**：激活时恢复两处，旧位置在前。旧位置是扩展自己的容器，以前的商店版把记录放在那里；只在那个文件夹已经存在时才查，不会去新建它。新位置是应用组容器。旧位置拒绝恢复，就保持只读，新位置不再去碰。新会话一律在新位置开始。实现是 `WriteJournalCoordinator.recover(stores:…)`；`NTFSVolume.recoverInterruptedWrites` 的日志拆成了 `reportRecovery`，官网版的行为不变。
- **旧位置收尾（审查发现后补上）**：插上盘激活时，设备还不能做持久刷新，所以旧位置回滚后，记录会留下并标成“已恢复”。原来这些记录由同一位置下一次开始写入时清掉，现在新会话只在应用组里开始，旧位置就没人清了。现在商店版开始写入前，会先对旧位置做同样的收尾（`WriteJournalCoordinator.retire`）：
  - 已恢复的记录：设备刷新之后删除；
  - 还没恢复的中断记录：拒绝写入；
  - 正常结束的记录：留给恢复去判断。

  没有这一步时用驱动试过：下一次连接，旧位置又回滚了一遍（写了 24 块），连带把新会话的写入也退回了。
- **已知的小代价**：以前的商店版正常结束后，如果盘在 20 秒保留窗口内被重新挂上，升级后第一次会话不会接续它，那最后一批写入的拔线保护会丢失。旧记录之后会被判为“之后被改过”而丢弃，不会回滚新写入。
- **方案一的代码保留**：只删记录目录本身时，它仍然管用。
- **测试脚本**：`scripts/test-fskit-journal.py` 找记录时也会查应用组容器。
- **驱动测试**：新增 5 项。`--quick` 共 15 项，arm64 和 x86_64 都通过；完整矩阵 1473 项通过（arm64）。三种构建都能编译。新增的 5 项是：
  - 记录在旧位置：恢复后回滚，新会话在新位置正常；
  - 旧位置是“已恢复”（没有设备刷新）：下一次写入前被清掉，再连接两处都是 none，新会话的写入还在；
  - 旧位置有未恢复的中断记录：拒绝写入，记录保留；
  - 记录只在新位置：能恢复，也不会新建旧文件夹；
  - 旧位置记录损坏：拒绝恢复、不写盘、记录保留，新位置不碰。
- **系统挂载镜像实测（2026-10-16 上午，商店版测试包 = 6f76279 + 测试开关，提交 d224a03）：全部通过。**
