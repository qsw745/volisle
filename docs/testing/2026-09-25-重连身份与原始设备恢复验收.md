# 重连身份与原始设备恢复验收

日期：2026-09-25。证据目录：`.workbench/reconnect-20260925/`。

## 本次实现

恢复日志的卷匹配身份与每次连接的临时身份已分离。新卷键 `recovery-volume/v1:` 使用带长度编码的字段计算 SHA-256，字段包含受信原生层取得的 USB 分区指纹、NTFS 引导摘要、设备容量和扇区大小。USB 指纹沿用现有 IOKit 读取逻辑，绑定序列号、厂商/产品编号、分区位置和容量；磁盘名、端口、启动代号和 registry ID 不进入持久卷键，原始 USB 序列号不进入日志。

设备传输仍绑定本次系统启动、IOMedia registry ID、全新占用许可和已打开的字符设备句柄；并未为了支持重接而删除当前连接的逐次验证。恢复工厂依然只接受认证流程产生的短生命周期许可。

原生物理恢复入口每次核验占用时还会有界枚举 IOMedia：要求当前目标是唯一匹配的设备实例；身份缺失、重复、枚举失效或超出上限均拒绝。这个约束仅用于可写恢复，普通只读占用不因缺少 USB 序列号而新增限制。旧日志中的 `native-connection/v1` 绑定不会被自动转换为新卷键。

测试镜像没有物理 USB 序列号，因此 DEBUG 配置使用独立命名空间的文件设备号、inode 和创建时间指纹。镜像工厂仍核对原始文件身份、实际 hdiutil 映射、64 MiB 大小、未挂载状态和系统虚拟设备。正式构建排除镜像指纹工厂及该命名空间；不把镜像证据伪装成物理 USB 验收。

## 真正断开和重新连接的测试

`python3 scripts/test-native-recovery-reconnect.py` 仅创建新的 `.workbench/native-write-reconnect-*` 镜像。准备阶段保存独立完整基线，植入单块测试中断状态并持久保存认证日志；结束该进程，正常断开系统设备后，再连接并启动全新测试进程。恢复阶段从持久认证权威状态读取旧绑定，不根据新连接重建或覆盖旧绑定。

最终报告：`.workbench/reconnect-20260925/reconnect-result.json`。

| 场景 | 证据目录 | 结果 |
|---|---|---|
| 同一镜像重接 | `.workbench/native-write-reconnect-8p_mgr8v/` | registry ID 改变，卷键相同；恢复 1 块，两次视图校验与完成回执通过 |
| 内容完全相同的另一镜像 | `.workbench/native-write-reconnect-d2okhm6c/` | 引导及完整内容相同，但文件身份不同；设备准入拒绝，校验器未执行，无恢复写入 |
| 断开期间多出日志之外的修改 | `.workbench/native-write-reconnect-v26llqyq/` | 卷键相同，虚拟恢复视图与事先独立基线不符；拒绝写回，保留额外修改，不发布回执 |
| 设备编号变化 | `.workbench/native-write-reconnect-0qhy1136/` | 临时镜像占住原编号，目标从 `/dev/disk9` 改为 `/dev/disk10`；仍匹配原日志并完成恢复 |

最后一项正常断开后的全镜像摘要为 `7c4b0df16a9b21de2dae8e3f2b7f8190f240963544f02e8f026478f5726dd231`，与准备阶段独立基线一致。所有场景均核对新旧 registry ID 确实不同；失败路径的完整镜像摘要保持不变。目标及临时占号镜像均只正常断开，不使用强制卸载；只删除本次成功验证的新建镜像。

这四项走真实可写原始设备节点和持久认证日志，但测试块仍为人工植入，不代表已经把持续运行的 FSKit 文件系统接入完整恢复机制。

## 验证范围

新增 5 个身份策略测试覆盖稳定键、组成字段变化、缺失/临时/非法身份、异常几何/引导摘要和重复或缺失的当前设备匹配。核心回归报告 235 个入口、28 组，默认执行 231 个、条件跳过 4 个；这 4 个原生只读/占用入口随后全部在新镜像中执行通过。原始设备可写恢复 3 场景重新通过；App、后台、诊断工具和核心库 Release 构建通过。Release 正向入口与 7 项反向边界检查通过，新增确认镜像身份工厂不在 Release 模块中。具体结果见本目录的 `handoff.json`、`validation.log`、`write-regression/writable-runtime-result.json`、`readonly-regression/runtime-result.json` 和 `release-probes.json`。

本轮没有修改 NTFS C 引擎或普通镜像恢复执行器，因此没有重复上轮 372 项引擎矩阵；其历史结果不计为本轮重新执行。

## 边界与后续

持久身份是匹配条件，不是硬件密码学认证，也不单独授权写入。USB 元数据伪造、不同主机的不可区分修改、真正系统重启与物理 USB 重插尚未实测。两张克隆镜像拒绝验证的是 DEBUG 文件身份路径；物理重复 USB 身份的拒绝策略已有代码及单元覆盖，但还需真实硬件验证。

后台协议已检查：现有 `VolisleHelperProtocol` 只有状态、磁盘检查和挂载周期入口。新恢复代码仍没有作为 XPC 写入接口开放。后续必须把可信检查点策略、后台认证和 FSKit 持续日志一起接入，不能让客户端传入“已验证”标志或基线摘要替代后台核验。

64 MiB 全镜像检查点仍仅是本轮恢复验证方案；2 TB 卷的检查点建立/更新性能未解决。日常覆盖保存与权限、多卷长期负载、干净系统及系统版本兼容验收也尚未完成。

未替换安装包、操作 qsw、修改权限或发布网站/更新；6 项正式发布阻断保留。
