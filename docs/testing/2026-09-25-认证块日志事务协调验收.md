# 认证块日志事务协调验收

日期：2026-09-25。新增 `BlockJournalTransaction`，把已有认证日志存储的调用顺序收进一个原生组件。40 项协调专项、125 项真实 NTFS 引擎隔离场景、现有核心包 179 项测试通过。组件在 VolisleCore 源码中，尚未接入正式后台或 FSKit 持续挂载会话。

## 本轮实现

每个实际完整块按顺序处理：持久记录原字节与新字节 → 独立可信凭据提供者完成比较并更新 → 写设备。初始事务记录也必须先保存外部凭据，构造成功才允许调用写入。

提交分为两个阶段：先调用引擎的元数据排空操作，这个阶段允许继续通过同一事务记录和写入；再进入只允许刷新的阶段，刷新设备、持久追加提交记录、保存最终外部凭据，最后返回 `BlockJournalCommitReceipt`。提交凭据不是 NTFS 卷已 clean 的证明；传入的 checkpoint 只是调用方标识，本组件不会据此证明设备内容或解除 dirty。

日志、凭据提供者、设备、排空或刷新中的任意错误都会锁住本事务，只通知一次停止写入。回调即使捕获并吞掉内部错误，也不能恢复事务；回调里的重入写入、重入提交或关闭同样被检查。成功后禁止再次写入或重复提交，已有成功凭据不会被后续错误调用撤销。未提交就关闭不会隐式提交。所有操作要求外部串行执行，组件不提供跨线程同步。

`SaveAnchor` 的合同是：绑定完整设备/事务身份，对比旧凭据，独立持久保存新凭据，完成后返回精确的新值。返回错误可能意味着已经保存，只是回复丢失；组件不会直接重试或推断没有发生。测试使用单独的普通文件提供者，执行文件刷新、替换与目录刷新，它不是正式 root 后台的可信存储，也不提供对同用户篡改、整目录回滚的防护。组件无法检测一个虚假承诺已持久化的提供者，因此正式提供者仍是必要前置工作。

## 40 项协调专项

`scripts/test-block-journal-transaction.swift` 覆盖：完整顺序、排空期间的追加元数据、重复写同一块的连续原字节、成功后拒绝第二次操作；初始/写入/提交三个凭据阶段保存前失败、保存后失败及错误回执；日志写前、写后、持久化后故障；设备半写、排空失败、刷新失败、吞掉错误、回调重入、主动关闭、中止；记录/字节预算、非法范围或 checkpoint、凭据比较冲突。

其中 7 个场景使用实际子进程直接退出：日志领先凭据、凭据领先实际写入、设备半写、未提交写入、提交日志领先凭据、提交凭据已保存但尚未回复、提交成功后退出。父进程重新打开日志、凭据和普通文件设备，核对完整原始/新字节及提交状态。操作系统缓存仍存在，不等于硬件断电测试。

专项报告：`.workbench/block-transaction-fe3791ca-0794-4109-b885-8e507c8a5fcd/result.json`。

## 125 项真实引擎隔离验证

`scripts/test-block-transaction-engine.py` 直接编译当前 C 桥接、原生完整块写入组件、认证日志存储和新协调层。使用新建的 64 MiB 普通文件 NTFS 镜像，4 KiB / 16 KiB 块大小，分别创建文件和目录；每类实际创建均有 6 个块写入位置。

- 4 个正常事务、1 个提交成功后进程退出：提交保留，既有哨兵文件经独立 `ntfscat` 核对，普通文件创建结果可读取。
- 96 个逐点异常：设备拒写、完整写后退出、半写后退出、外部凭据已经保存但回复失败。Swift 重新打开并认证全部日志与外部凭据，随后测试专用 Python 恢复规划器先验证完整回滚计划，再修改隔离镜像；恢复后与最初完整镜像 SHA-256 一致，独立哨兵回读一致，干净可写重新挂载通过。
- 24 个外部凭据保存前失败：日志存在未确认尾记录，检查明确拒绝，检查前后镜像摘要不变；未尝试猜测或自动修复。

这里的事务覆盖“干净挂载 → 创建 → 干净卸载”。恢复执行仍是隔离镜像专用 Python 规划器，不是产品恢复实现，不代表同一持续挂载会话的逐操作检查点能恢复 clean，也不覆盖 Windows 插拔恢复。

引擎报告：`.workbench/block-journal-6bdgffnz/result.json`。成功场景新建镜像已由测试清理，日志和报告保留；既有四个失败镜像未修改。
