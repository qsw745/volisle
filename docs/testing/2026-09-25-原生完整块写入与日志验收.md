# 原生完整块写入与日志验收

日期：2026-09-25。本轮跨午夜执行，原始日志保留在 `.workbench/metadata-pipeline-20260924/`。结论：扩展实际使用的 Swift 块写入组件完成接入；测试用原生日志与真实 NTFS 引擎组合通过 101 项隔离验收，组件自身 30 项通过。正式应用尚未接入块日志存储、逐操作提交与恢复流程，发布阻断不变。

## 接入源码的变化

新增 `apps/extension/Sources/MetadataWritePipeline.swift`，由 `NTFSVolume.devicePwrite` 调用。读改写不再按整个请求分配大缓冲区，而是一次处理一个固定缓存块，包含设备末尾的短块。设备大小、偏移、输入长度、块大小及算术边界在回调发生前检查；块大小限制为不超过 1 MiB 的正二次幂。

组件提供“读取完整旧块 → 持久记录完整旧/新块 → 写出完整块”的同步调用顺序。传入记录回调时，即使引擎请求完整覆盖某个块，也先读取旧块；只修改几个字节时，日志同时覆盖实际会写出的邻接字节。生产扩展当前未传入记录回调，不得把组件已经链接理解为正式日志已经启用。

任一读取、记录或写入步骤失败，组件锁住本次实例，不尝试第二种 I/O 路径，也不允许后续写入。`NTFSVolume` 的可写激活原本就要求元数据缓存可用；本轮进一步删除了探测态的普通直写备用分支，写回调只允许元数据缓存模式。正常激活流程原本不会使用该备用分支，因此这里是加强约束，不是声称正常挂载已经复现了该分支导致的数据损坏。

本机 Apple SDK `FSResource.h` 要求同一区域固定缓存范围，并明确不能混用直接 I/O 与元数据缓存 I/O。写入组件继续采用原有 `MetadataBlocks` 的相同块网格；只读激活前的探测读取逻辑没有修改。

## 组件测试：30 项

`scripts/test-metadata-write-pipeline.swift` 使用与扩展同一份 Swift 源码，覆盖：

- 512 B、4 KiB、16 KiB 的整块、局部、跨块、零长度和尾块请求；邻接数据保留，记录的范围与写出的范围一致。
- 读取失败、记录失败和写入失败的顺序约束，以及失败后不能继续写入。
- 非法块大小、越界、负偏移、整数边界在任何设备回调前拒绝。
- 没有记录回调时，整块写入无需额外读取；多块请求的单次缓冲区仍不超过一个块。
- 第二块日志失败或部分写入失败时，第三块不被修改；回滚已记录完整块可恢复起点。

先以未实现写入组件确认测试失败（`red.log`），实现后通过（`green.log`），再增加第二块失败场景，最终 30 项通过（`final-unit.log`）。原 `test-metadata-blocks.swift` 的固定缓存键、位图更新、尾块和越界回归也通过（`cache-regression.log`）。

## 真实引擎与原生日志：101 项

`scripts/fixtures/metadata_pipeline_driver.swift` 编译同一个组件，链接当前 C 桥接与 libntfs-3g。底层只接收工作区新建的、单链接、当前用户所有的 64 MiB 普通 NTFS 镜像；对镜像持有排他锁。没有挂载真实磁盘或启动 FSKit 服务。

测试专用 Swift 记录器对每个实际完整块写入生成原/新字节日志，先写日志文件并 fsync，再调用镜像写入；文件创建目录项也刷新。记录格式兼容上一阶段 Python 恢复验证器，恢复前校验身份、摘要链与完整回滚计划。该记录器不链接到正式扩展，不是可信后台日志方案。

4 KiB 和 16 KiB 两种块粒度下，创建文件及创建目录各有 6 个实际块写入位置。每个位置分别测试：

1. 镜像写入返回失败。
2. 写入后子进程直接退出。
3. 只写出半块后刷新并退出。
4. 持久记录前模拟日志空间不足。

共 96 个故障场景，另外 4 个正常提交场景，以及提交已落盘后进程退出保留新文件，共 101 项。每个回滚场景核验：全镜像 SHA-256 与起点相同、旧哨兵文件经上游独立 `ntfscat` 回读一致、重复恢复零写入、卷预检 clean、能够正常重新打开和关闭写入会话。

结构化报告 `.workbench/block-journal-mw9whv3p/result.json`；执行日志 `native-matrix.log`。覆盖此前已知 MFT/MFTMirr 中断位置在“存在完整块日志”的受限场景，不能据此删除无日志正式驱动的阻断。

## 编译与范围

日常可写与默认只读两种 FSKit 扩展配置均在本机编译，并验证系统扩展入口。日常可写产物单独归档为 `VolisleFS.daily` 与 `daily-build.json`，没有安装或注册；默认配置回执见最终交接记录。

与上次 Python 常驻会话原型不同，本次原生记录器故障矩阵的单笔事务包含干净挂载、一次创建和正常卸载，成功只在事务提交后对测试调用方确认。因此能回滚至原来的 clean 镜像。这里不能回滚用户长时间挂载期间已经保存的操作，也不替代上次逐操作提交验证；更不能把它当作 dirty 检查点安全清理方案。

仍未完成：可信且有容量上限的正式日志存储、FSKit 操作级提交与错误传播、系统缓存失效/重建、设备身份绑定、恢复授权、常驻挂载恢复到可写、直接连接 Windows/其他电脑的跨主机恢复。本轮是普通文件上的同步 I/O 与受控退出/半块写入，不是实际 FSKit 运行、物理断电或任意扇区撕裂验收。
