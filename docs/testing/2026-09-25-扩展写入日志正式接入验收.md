# 扩展写入日志正式接入验收（R1 / R2 / R3）

日期：2026-09-25。本轮只使用新建的一次性镜像（64 MiB、512 MiB、2 TiB 稀疏）；未操作 qsw 2 TB，未改系统设置，未发布。

## 方案变化与原因

此前的认证日志组件（`BlockJournalAuthority` 等）设计为 root 后台持有权威状态。核对源码后确认两点，使其无法直接接入日常写入：

1. FSKit 扩展运行在沙盒内，不能访问 `/private/var/db/volisle`，扩展与 root 后台之间也没有通信通道。
2. 现有日志每记录一个 4 KiB 块就做两次 `F_FULLFSYNC`，并且单事务上限 4096 条、64 MiB，日常复制几 GB 文件不可用。

因此正式路径改为**扩展内会话撤销日志**，放在扩展自己的沙盒 `Application Support/VolisleWriteJournal`（与已有覆盖实验记录同一位置，路径只来自系统，不接受磁盘或挂载参数）。沿用已有成果：整块写入管线 `MetadataWritePipeline`、桥接层“只释放本会话自己设置的脏标记”规则（`clear_owned_marker`）、只读预检、HMAC 帧链思路。旧组件保留在 VolisleCore 作为隔离测试，不在正式调用链中。

HMAC 用于识别撕裂和损坏的记录，不作为针对扩展自身账户的安全边界（该账户本来就能写设备）。

## 工作方式

- 引擎的每次设备写入都先进入内存待写块；每累积 8 MiB 或引擎要求刷新时形成一组：先把本周期内首次改动块的原内容与所有新块摘要写入日志并 `F_FULLFSYNC`，然后才写设备。
- **检查点**只在操作边界打：`nk_sync` → 写入剩余组 → 设备刷新 → 写检查点记录 → 删除本周期日志。触发条件：同步请求、卸载、空闲 1 秒、周期满 5 秒、周期原内容累计 32 MiB（每个写操作开始时也检查，避免连续复制时定时器抢不到锁）。
- 单周期原内容硬上限 256 MiB，超出即停止写入会话（不继续增长）。
- **下次连接时恢复**：激活阶段、可写预检之前执行。核对设备大小、块大小、引导扇区、`$LogFile` 开头摘要（Windows 挂载会改写，本桥接取证模式从不写）；逐块核对当前内容只能是原内容或日志记录过的新内容（最后一组允许撕裂）；再从新到旧回滚未完成周期；最后在一个同样记日志的“恢复周期”中释放本会话自己设置的脏标记，并要求 `nk_inspect` 为 CLEAN。任何一项不符即拒绝、保留记录并只读挂载。
- 激活阶段只有同步直写、没有设备刷新屏障，因此恢复完成后记录标为 `recovered` 并保留，到下一次可写会话开始时先做设备刷新再删除；若之后再次连接时仍存在，会先重新核对回滚结果。

## 边界与已知限制

- 以上是镜像上的引擎级验证；真实 FSKit 挂载、Finder 使用和物理拔插须在安装候选后实测（见当前交付清单 R1/R6）。
- 只有最后一组内的块无法逐块识别外部修改，此时依靠引导扇区和 `$LogFile` 哨兵识别其他系统的使用。
- 异常中断会丢失上一检查点之后的写入（通常不超过数秒），换取卷结构一致；不会伪造成功。
- 文件数据块也记录原内容，写入新文件时会额外读一次设备；性能数字来自本机 SSD 上的镜像，USB 实盘速度须另测。
- 日志位于 Mac 本机磁盘，单个卷最多占用约 256 MiB。
