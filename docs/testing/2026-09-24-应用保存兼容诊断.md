# 应用保存兼容诊断

2026-09-24，Apple Silicon / 本机 macOS 27.2。本轮确认了阻止正式产品开放的一项实际兼容问题，**尚未修复应用内保存**。

## 结论

在精确绑定的可丢弃 NTFS 镜像上，使用系统“文本编辑”打开新建的 UTF-8 文稿，编辑并保存，连续两次隔离实验均出现“未能保存文稿”。扩展日志精确记录了私有文件 0600 和私有目录 0700 请求被 ENOTSUP 拒绝。当前 FSKit 属性实现只支持普通文件 0444/0644、目录 0755；此失败发生在应用保存的临时文件/目录准备阶段，不能通过打开同名替换开关解决。

TextEdit 关闭时还显示版本储存相关提示，其中的“更改已保存”与实际文件内容不符。本轮以磁盘字节核对为准，没有将此提示视为保存成功。仅对新建测试文稿选择复原并关闭，其他已打开文稿未编辑或关闭。

## 实现与验收

- 新增属性拒绝日志，仅记录目录类型和八进制权限，不记录文件名、路径或内容。
- 扩展 `scripts/test-fskit-replacement.py`，增加真实应用连续两次保存验收、逐阶段内容核对及只读重挂载核对。
- 为已知不兼容流程增加单独的保护性验收模式。结果明确写入 `application_save_supported: false`；其 `success: true` 仅表示“拒绝后原文件保留”的保护检查通过，不能作为保存兼容通过。
- 新增实际私有文件/目录创建检查：0600 与 0700 返回 ENOTSUP，没有留下权限被放宽的节点；增加目录 0700 的属性单元检查。
- 日常界面沿用现有的一行提示，明确 Finder 复制能力与应用内覆盖保存尚在适配；没有增加设置页或复杂操作。

## 下一步完成条件

需先实现并验证私有文件/目录权限的持久化与访问控制，再进行真实应用保存。不能把 0600/0700 请求转换成共享权限并返回成功；也不能只在内存中记住权限，导致重挂载后开放访问。

NTFS 用户标识与 macOS 用户身份不同，后续实现需要确定映射与无映射行为，验证不会错误改写已有 Windows ACL、导致 Windows 用户失去访问或让其他 Mac 用户获得访问。上游说明见 [NTFS-3G 文件所有权和权限](https://github.com/tuxera/ntfs-3g/wiki/File-Ownership-and-Permissions)。本轮没有修改 Windows 安全描述符，也没有新增权限映射实现。

完成该基础后，需重新通过 TextEdit 连续保存、关闭重开、只读重挂载，以及其他文稿类应用的保存路径。随后才可评估日常版开放同名替换；Windows 实机、断电/热拔插、自动更新、公证与公开发布仍待完成。

本轮未对 qsw 2 TB 实体盘执行挂载、读写、格式化或删除；完全磁盘访问保持原设置。
