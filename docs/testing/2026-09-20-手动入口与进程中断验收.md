用户请求正式开放写入，随后明确说明 2 TB qsw 盘没有完整备份。当前不是正式读写版，本轮未向该盘放开写入，未卸载或修改它的已有文件。工作继续在一次性镜像上执行。

## 已完成的产品改动

- 主界面增加“启用读写”入口，连接手动操作控制器和已有挂载协调器；按钮只在真正的写入适配器报告能力时可用。
- 主应用用真实 FSKit 查询替换固定的“引擎不存在”状态：核对唯一扩展、启用状态以及扩展是否属于当前应用副本；查询超时和错误均拒绝宣称可用。
- 当前适配器明确为 `ReadOnlyFSKitEngine`，始终不授予写入能力。已安装扩展不等于已通过写入验收。写入适配器、风险检查和实际手动挂载仍未打通，不能把 UI 入口接入描述为写入功能完成。
- 手动控制器拒绝重复点击、已可写/未知状态的选择和已取消的请求。只有挂载返回后再次确认相同卷身份、实际可写状态与挂载路径，才显示成功消息。
- 实际 GUI 已显示 `qsw NTFS · 只读`，按钮禁用，解释为“扩展已启用；此版本仅开放读取，写入验收尚未完成。”没有要求用户再次启用已经开启的权限。

## 找到并修复的实际故障

进程中断后脏卷的写入被拒绝，但原代码先关闭只读引擎，再尝试打开写引擎；写引擎失败后留下空句柄，后续读取也返回错误。

修复为：失败后重开只读引擎，原写请求仍报错，并锁定本次会话不再尝试写入激活。若只读恢复也失败，则保留失败状态。此处理不修复 NTFS、不清脏标记，也不把失败写入改成成功。

注意：实验挂载仍采用延迟写入激活，内核挂载标志为可写不代表引擎最终接受写入。产品正式适配器仍需完成挂载前风险检查，不能靠 `statvfs` 标志单独放行。

- 首次样本 `.workbench/fskit-readonly-4e1dpuyv`：独立 `ntfscat` 默认拒绝读取脏卷，脚本未完成。后续按上游工具只读模式启用脏卷读取，并核对读取前后完整镜像摘要不变；不执行修复。
- 故障复现 `.workbench/fskit-readonly-stkxkf92`：写入被 EIO 拒绝后，查询不存在文件返回 EINVAL，暴露只读句柄丢失。原镜像及失败记录保留。
- 修复样本 `.workbench/fskit-readonly-0rq3gb9h`：5 项通过。已 fsync 的数据在进程被 SIGKILL 后仍由独立工具正确读出；脏卷只读重挂成功；连续三次写入均拒绝；每次拒绝后原测试内容和种子文件仍可读；后续完整镜像摘要不变。三个挂载会话全部正常释放。
- 正常回归 `.workbench/fskit-readonly-p82908xn`：19 项、100 份文件独立核验及分配检查通过。它是异常测试开始前复制的、校验值相同的干净普通镜像，不是对故障样本修复或重置。
- 核心测试 49 项通过，包括新增 6 项手动操作与 2 项扩展状态检查。应用和扩展均在本机重新构建及签名。

这次终止发生在普通数据 fsync 完成后，不覆盖正在写入中、覆盖事务中、断电/USB 拔插、撕裂扇区及 Windows 检查。不能推导所有异常中断都安全。
