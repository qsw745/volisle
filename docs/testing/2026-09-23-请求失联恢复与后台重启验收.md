# 请求失联恢复与后台重启验收

## 行为

- 客户端启动时对保存的请求发送 `resolve / resolveWrite`，不重复启动挂载。
- 若存在相同操作，必须匹配请求编号、设备身份、用户和读写用途，继续跟踪及核验。
- 若没有相同操作，后台先持久保存该请求编号的拒绝重放凭据；客户端只在收到匹配凭据后清理旧请求，并继续核对当前后台操作。凭据不能证明磁盘已挂载或只读。
- `requests.json` 保存在后台已有的 0700 私有目录；0600 普通文件、禁止链接、容量限制、同目录原子替换、文件及目录同步。后台准备阶段尚未生成操作记录时拒绝结束请求，避免晚到的挂载越过界面锁定。
- 所有新接收请求也先登记编号。因此第一项操作完成、第二项完成之后，第一项编号仍不能重新执行。已有旧格式当前记录在被替换前迁移。
- 请求账本最多 16,384 项、16 MiB，不自动淘汰记录。满额或写入持久化失败时拒绝新工作；不为继续写盘而清空记录。这是仍需产品化维护的明确上限。
- 断开证明改为先确认 IOKit 查询成功、迭代器有效，再判断设备是否消失；查询失败不会被当成拔盘成功。
- 新后台活动开始时清除上次推出提示，避免“可读写”和“设备已推出”同时出现。

## 尚未覆盖

没有在本轮重跑已通过的 19 组 FSKit 文件读写用例（桥接及扩展文件写入实现未改变）。没有执行带活动写入的 helper 崩溃、真实热拔插、断电、完整磁盘满矩阵或 Windows 检查。没有公证或公开发布。

同名替换保存和私有权限仍未在日常候选开放。私有权限需遵循 NTFS 安全描述符及账户映射，不可仅把返回值改为成功或把 0600 文件实际建为 0644。已核对固定上游 `libntfs-3g/security.c` 的 `ntfs_build_mapping / ntfs_get_owner_mode / ntfs_set_mode` 及 [上游权限说明](https://github.com/tuxera/ntfs-3g/wiki/File-Ownership-and-Permissions)。默认映射不能作为既有 Windows 账户互通已验证的证据；后续先做可丢弃镜像的原生 ACL 往返验证，再接 FSKit 权限请求。
