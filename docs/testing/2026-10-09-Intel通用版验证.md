# Intel 通用版验证（无 Intel 真机）

日期：2026-10-09。本机为 Apple 芯片 Mac，Rosetta 2 可用。目标：安装包同时包含 arm64 与 x86_64，Intel 版以“测试版”对外。

## 构建
- NTFS-3G 静态库一次编两个架构（`-arch arm64 -arch x86_64`）；config.h 未定义 `AC_APPLE_UNIVERSAL_BUILD`/`WORDS_BIGENDIAN`（两者都是小端 LP64，一份配置适用）。
- NTFS 引擎、mkntfs、ntfsrecover、扩展的 C 部分同样双架构；扩展 Swift 部分按架构各编一次再 `lipo`，入口校验逐架构进行。
- Sparkle 以 `ARCHS="arm64 x86_64"` 编译；App 与后台组件用 `swift build --arch arm64 --arch x86_64`。
- 产物名改为 `Volisle-<版本>-universal.dmg` / `-universal.zip`；官网脚本兼容历史 `-arm64` 名称。
- 安装包内 8 个可执行文件（App、后台组件、扩展、Sparkle 5 个）均为 `x86_64 arm64`；扩展声明、App/扩展/后台组件权限与 LaunchDaemon 配置的哈希与已发布版一致。

## 发现并修复的问题
Intel 架构下 Windows 日志恢复测试以 SIGFPE 崩溃。用 `-fsanitize=integer-divide-by-zero` 在原生 arm64 上定位到 ntfsrecover `getboot()`：盘屿补丁让它改用后台传入的设备，跳过了原本读引导扇区的 `fread`，却仍解析未填充的 `boot.buf`，得到“每簇扇区数 0”后整除。Intel 上整数除零直接崩溃；Apple 芯片上得 0 继续，簇大小与 MFT 记录大小取自栈上残留内容（重放按簇读写时依赖它们）。修复：外部设备挂载成功后用 `ntfs_pread` 读出前 1024 字节再解析。修复后带除零检查的构建不再触发，两种架构重放结果一致（日志 2.0、补写 2 项、核对 9982 项、基线 160 完好 40 按预期删除）。

可能相关：2026-10-08 实体 Windows 11 拔线盘的重放停在 “UpdateFileNameAllocation (action 16) not acting on INDX”，当时只能放弃日志；在该缺陷修复后值得重测。
