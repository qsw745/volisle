# 改名故障与打开文件验收

本轮为覆盖保存补齐前置能力：改名预检、失败后的名称保留、写入/同步故障检查，以及打开文件的改名、目录移动和删除语义。**未开放覆盖保存，也未宣称改名具备断电原子性。**

## 改动

- 复现并修复同名改名错误；同一 inode 的无变化改名成功且不产生修改回调。
- 目标已存在时在链接前返回 `EEXIST`，不触碰源文件和目标文件；目标不是目录时拒绝。
- 使用真实 inode 父目录链检查目录循环，拒绝移入自身及后代。检查不只依靠字符串前缀；异常父链最多遍历 1,024 层后拒绝。
- 新名称链接完成后检查两份 inode 关闭结果，并调用同步，然后才删除旧名称，最后再同步。错误不能因忽略 inode 关闭结果而被掩盖。
- 取消失败后主动删除新名称的回滚。在旧名称是否已经删除、是否已持久化不明确时，应保留已有名称，报告失败并锁定写入会话。

此前的“同名改名失败”有红灯测试证据。潜在的回滚风险由控制流审查识别，本轮没有声称旧实现已在真实盘造成数据丢失。

## 普通文件镜像故障矩阵

`scripts/test-ntfs-rename.py` 创建新 64 MiB 普通镜像，放入待改名文件和独立哨兵文件；从不 attach，不接受任意设备路径。所有失败后的内容核验使用独立上游 `ntfscat`，异常镜像仅以该工具的只读模式检查，不做修复。

| 场景 | 结果 |
| --- | --- |
| 同名改名、目标冲突、目录循环 | 预期结果及零修改回调通过，正常关闭后仍为干净卷 |
| 普通改名成功 | 新名称内容一致，旧名称不存在 |
| 第 1–7 个写入回调分别失败 | 全部返回错误、阻止后续修改、关闭报错并保留 dirty；至少一个名称可读回原内容，哨兵不变 |
| 第 1–2 个同步点分别失败 | 返回错误并保留 dirty；至少一个名称可读，哨兵不变 |
| 第 1–7 个完整写入回调结束后进程立即退出 | 父进程独立核验原内容可由旧名称或新名称读取，哨兵不变；再次写挂载被预检拒绝且没有写回调 |

退出由测试子进程在自己的镜像回调内执行，跳过桥接关闭。退出前 fsync 普通文件，模拟已持久化的完整写入前缀；**没有模拟扇区撕裂、硬件缓存重排、真实断电或 FSKit 进程终止**。部分检查保留两个名称，部分只剩新名称，这是失败状态的可恢复入口，不是命名空间原子性证明。

原始结构化结果：`ntfs-rename-result.json`。测试目录在结束后清理，未修改用户磁盘。共有 7 个写入故障点、2 个同步故障点和 7 个退出点。

## FSKit 系统挂载

使用镜像 `.workbench/fskit-readonly-rpjj0sqa` 和签名候选 `apps/macos/build/signed-rename-check`。

19 项系统检查通过，包含新增的：

- 文件描述符保持打开，改名后继续读取和写入，关闭后新名称内容正确。
- 子文件保持打开，移动父目录后继续通过原描述符读写，新路径内容正确。
- 文件保持打开时删除目录项，路径消失，描述符仍能读写直至关闭。

同时通过原有精确时间、权限拒绝、扩展属性、64 轮分配删除、正常卸载、100 份预期文件的独立哈希检查、只读重挂、写入拒绝及分配检查。123 条 MFT 记录和 1,281 个占用簇未发现所检查的重叠或位图不一致问题。这个检查不是完整 NTFS 检查。

结果：`fskit-rename-result.json`。这轮没有重新进行 Finder GUI 操作；此前 Finder 验收不能冒充本轮新证据。核心 41 项、既有桥接 21 组及精确时间 6 项检查也通过。

## 覆盖保存仍需解决

目标文件已有打开句柄时，必须保留旧对象供原句柄使用，同时让新路径指向新对象；当前路径缓存不能直接当作稳定 inode 身份。替换过程还需要可识别的恢复状态、失败/退出后的处理，以及独立验证完整性。不能简单删除目标再调用普通改名。

下一步先建立替换状态与恢复策略，明确失败时旧内容、新内容及名称的可见性，再进行专门的原型和故障矩阵；Windows 检查、物理持久化及断电测试依然缺失。

本轮完成后恢复 `signed-rename-readonly` 默认只读安装，最终实测状态见 `fskit-rename-installation.json`。用户 2 TB `qsw` 保持只读，未在其中写测试数据或改动已有文件；没有公开发布或修改 UI。
