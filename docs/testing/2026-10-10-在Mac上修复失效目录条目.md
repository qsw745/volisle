## 已在云端验证（Linux，不是本机）

云端没有本机的 `.workbench`。为了跑引擎测试，在临时目录里从 GitHub 上游取了 ntfs-3g **2026.7.7 标签**源码（与本机同一版本），按 `prepare-ntfs-probe.py` 的 configure 参数编译 libntfs-3g，按 `build-mkntfs.sh`、`build-ntfsrecover.sh` 打补丁编译 mkntfs/ntfsrecover，再编桥接测试库。macOS 专有的部分用了临时替身，只放在临时目录、没有进仓库：CommonCrypto（BitLocker，测试不涉及）、文件名 NFC/NFD 规范化、`ENOATTR`、`optreset`、`uuid_generate`。

- 桥接编译：`-Wall -Wextra`，新代码（`check_marker.inc`、`stale_entry.inc`）没有警告。
- `scripts/test-ntfs-stale-entry.py`：**18 项通过**。
  - 检查：失效条目（记录被重用 / 记录空闲 / 先经合法条目到达）都判为 `stale entry`，带文件夹记录号和两个不同的序列号；序列号相同的类型不符仍报原来的种类；全部零写入。
  - 修复：只删失效条目；被重用的记录逐字节不变，新文件内容不变，同文件夹其余条目都在，Windows 日志开头不变；之后检查通过，NTFS-3G `ntfsfix -n` 通过。覆盖条目在 INDEX_ROOT、在索引块里（60 多个条目的文件夹）、原本没有“需要检查”标记三种情况。
  - 拒绝且零写入：序列号相同的类型不符；被重用的记录只能经失效条目到达；仍有在用记录以旧文件夹为上级；没有失效条目；Windows 休眠；Windows 维护未完成。
  - 中断：修复的每一次写入分别出错（3 / 5 / 3 次写入，对应带标记 / 不带标记 / 索引块三种盘），按撤销记录还原后镜像逐字节等于修复前；每一次写入后进程直接退出，盘始终标着“需要检查”或读不出（$MFTMirr 与 $MFT 不一致时 NTFS-3G 拒绝挂载），Windows 日志开头不变，用遗留撤销记录可原样还原；只有最后一笔写完才变干净，此时修复已完成。
- 回归：`test-ntfs-check-marker.py` 6 项、`test-ntfs-format.py` 8 项、`test-ntfs-symlink.py` 3 项通过。
- `test-ntfs-bridge.py`、`test-ntfs-names.py` 在 Linux 上失败，原因是环境（Python 没有 `errno.ENOATTR`；文件名规范化是替身），与本次改动无关，需本机确认。
- 界面文字：英文、简体表手工补 45 条；繁体用 `make-zh-hant.py` 生成（opencc 装在临时虚拟环境；先确认它对现有表重新生成结果完全一致）。
