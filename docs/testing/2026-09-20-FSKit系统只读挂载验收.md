## 修复及证据

首次运行 `.workbench/fskit-readonly-krmpt6mv` 在 ExtensionFoundation 初始化时崩溃，尚未进入 NTFS 操作。崩溃报告为 `~/Library/Logs/DiagnosticReports/VolisleFS-2026-09-20-160154.ips`。对照本机 Xcode 扩展目标的成功构建命令，发现直接 Swift 编译缺少系统扩展入口。

- `scripts/build-fskit-extension.sh` 增加 `-application-extension` 及链接入口 `_NSExtensionMain`，保持默认只读。
- 新增 `scripts/verify-extension-entry.py`，静态检查 Mach-O 入口不直接进入 Swift main、且引用系统扩展入口；旧产物检查失败，修复产物及当前已安装产物检查通过，不执行被检查文件。
- 编译与签名流程均运行入口检查。签名脚本新增 `--output-dir`，仍拒绝覆盖，允许保留旧候选并生成新候选。
- 本机重新构建、Developer ID 签名并验证后安装修复包；旧安装包先核对再归档。新签名候选位于 `apps/macos/build/signed-entryfix`，旧安装包归档为 `apps/macos/build/installed-before-entryfix.tar`。
- 安装后签名 `codesign --verify --deep --strict` 通过；构建清单与描述文件回归合计 23 个场景通过。

第二次运行 `.workbench/fskit-readonly-8bb2fjwu`，扩展成功启动、接收资源并激活卷，但最终挂载返回 EPERM。FSKit 系统日志明确显示调用方 uid 501，而挂载目录实际所有者被守护进程识别为 99；挂载目录位于忽略所有权的外接 APFS 工作区。

`scripts/test-fskit-readonly.py` 因而改用 `/private/tmp` 下由当前用户独占新建的目录作为挂载点，并在正常 detach 后仅删除自己的空目录。镜像仍位于工作区；没有修改外接 Data 卷的所有权设置或系统保护。第三次使用全新镜像测试全部通过。两次失败镜像也均正常 detach，内容哈希未变。
