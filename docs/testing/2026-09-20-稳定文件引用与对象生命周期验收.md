# 稳定文件引用与对象生命周期验收

本轮将 MFT 记录号与序列号组成的文件引用接入 FSKit 数据读写、属性读取，并替换原有仅按路径复用的对象缓存。**未开放 FSKit 覆盖保存，未自动清理恢复副本。**

## 引用访问与过期对象保护

桥接新增 `nk_reference_path`、`nk_stat_reference`、`nk_read_reference`、`nk_write_reference`。引用包含 48 位 MFT 记录号和 16 位序列号，限定在当前卷的挂载生命周期内使用，不作为跨卷或跨重挂的持久凭据。

上游 `libntfs-3g/inode.c` 的缓存命中只按记录号查找，并跳过真实打开时的序列号验证。本实现每次取到 inode 后主动检查在用标志和实际序列号。序列号为零的引用拒绝；记录已释放或复用时返回错误，不转向新占用者。

这不是“打开并固定 inode”的句柄：它不会阻止文件删除或记录复用。旧文件必须保留一个磁盘名称，直到所有仍可访问它的对象结束生命周期。NTFS 序列号只有 16 位，不能替代名称保留或被视为永久身份。

## FSKit 接入

- `NTFSItem` 持有不可变 `fileReference`。数据读写和属性查询按引用调用桥接，改名不会改变该引用。
- 创建子项、查找/枚举目录、删除、改名、设置属性、符号链接读取、扩展属性等仍使用路径的操作，先核验路径当前引用与对象一致；操作整体互斥，避免本模块在核验与执行之间换名。
- `ItemIdentityCache` 区分同一路径上的不同引用，创建新对象与文件标识；不会把旧对象身份改成新文件。旧对象的延迟回收或删除不会驱逐新对象。
- 普通回收后重新查找同一文件保留文件标识；目录移动保留已有对象、子对象路径和仅枚举过的子项标识。当前标识仍为挂载期分配，不是跨挂载持久 ID，也没有声称完成硬链接别名语义。

这些修改解决了替换前置的对象身份问题。`renameItem(overItem:)` 仍返回不支持，开发镜像的保留版本替换原型仍被独立 C 构建宏隔离。

## 验证

新增测试先在未实现的引用接口和对象缓存上出现预期失败，再完成实现。

`scripts/test-ntfs-reference.py` 的 7 组普通镜像检查通过：

1. 先保存新旧引用，再用开发替换原型改变名称。旧引用读旧内容、目标路径解析到新引用；分别写入两个引用后，内容互不影响，属性长度正确。
2. 正确 inode 已缓存时，伪造/为零的序列号仍被拒绝，零写回调。
3. 非法范围和目录引用不能当普通文件读写，拒绝发生在修改前。
4. 删除备份名称后真实触发 MFT 记录复用，旧引用读写拒绝、新文件内容保持不变。不是仅用一个人为错误编号代替实际复用。
5. 正常关闭后使用独立上游 `ntfscat` 核验目标与新占用者内容。
6. 只读重新打开后重新解析引用，读取正常、写入拒绝、镜像全量哈希不变。
7. 引用写入失败或短写后会话锁定，关闭报错、dirty 保留。

结果：`ntfs-reference-result.json`。这是 C 引用语义，不是 macOS 文件描述符的覆盖测试。

`scripts/test-item-identity.swift` 在真实 FSKit 类型上验证：路径重新绑定、旧对象回收、源对象移动、目录子对象及枚举标识迁移、MFT 序列号变化、普通回收后的重新查找、根目录标识。测试没有模拟内核调度，也未把它算作系统覆盖保存验收。

## 副本清理边界

本机 macOS SDK 的 `FSVolume.h` 指定，覆盖操作应将旧对象标为删除，并在其 `reclaimItem` 时释放空间；`closeItem` 还会带有保留的访问模式。因此不能将一次关闭回调当作最后一个引用结束，也不能在替换返回时立即删除旧副本。

本轮引用测试还允许旧引用继续写入旧副本。此时上一轮恢复计划中记录的替换前哈希不再描述当前副本内容；该工具依然严格拒绝与记录不符的内容，不能将它宣称为支持后续任意写入的恢复机制。

下一步需实现替换状态的持久化、旧对象继续写入时的恢复记录策略，以及 `reclaimItem` 时再次核对副本路径/引用和提交状态的受控清理。中断或身份不确定时保留副本，不进行自动删除。Windows 检查、扇区撕裂、硬件断电和最终产品验收仍未完成。
