# 小红书反馈：4TB 硬盘恢复耗时与取消置灰排查

日期：2026-10-19。检查基线：`5ad73f2`，并对照 `v0.9.4` 确认下列关键代码也存在于该标签。反馈者的盘屿版本未确认，所说约 27.2 按系统版本线索处理。

## 已知现场与结论边界

反馈者称修复耗时一个多小时，取消禁用；中间借助 AI 尝试结束/退出，具体执行命令未知；后来提示成功，也有已记不清的异常提示，当前硬盘能正常使用。没有当时的诊断、精确版本、簇大小、文件记录数或命令记录。

不能据此证明正常完成、没有发生过问题，或把一小时归结为硬盘容量。代码检查和本地实验已证实大盘读取上限冲突、完成状态反馈不完整，并测得大量小块读取；这些是可独立处理的缺陷/风险，不等同于锁定这一次的唯一根因。

## 1. 已复现：4TB / 4KB 簇空间位图超过原始读盘接口上限

- `check_marker.inc:186` 一次读取整个 `$Bitmap`。
- `MaintenanceEngine.swift:23-27` 对齐后的单次原始 I/O 上限为 64 MiB，超出即置 `failed` 并返回错误。
- NTFS-3G `attrib.c` 按属性物理运行段转发读取，连续的位图没有自动按 64 MiB 分块。

用本地 `mkntfs -F -Q -s 512 -c 4096` 创建 4,000,000,000,000 字节稀疏普通文件镜像，实际占用约 190 MB。标记需要检查后，使用当前源码重新编译的原生桥接库，分别注入与应用相同的 64 MiB 单次读取限制、以及不加此限制的普通文件回调：

| 条件 | 结果 |
| --- | --- |
| 64 MiB 上限 | 请求 122,070,320 字节，拒绝，`rc=-1`，`read failed at record 0` |
| 接受同一读取 | `rc=0`，清除检查标记成功，耗时约 0.33 秒 |

证据：`.workbench/xhs-recovery-20261019/probe.py`、`four-tb-result.json`、`mkntfs.log`。镜像已删除，未操作实体盘。实验使用原生检查引擎及等价上限回调，没有经过真实原始设备或系统挂载。

影响：满足相应簇大小和位图运行段布局的大盘可能在检查后半程报软件自身限制导致的读错；若之前已经补写，外层会尝试还原。不说明故障硬盘、坏扇区，也不单独解释一小时。

修复方向：将属性/位图读取拆为有界小块，保留全部检查；不要直接取消原始 I/O 的内存边界，也不要跳过空间分配核验。

## 2. 已测量：恢复有显著的小块读取放大

`check_volume_walk` 先遍历目录与文件记录，随后 `check_allocation` 按 `$MFT` 初始化长度再次逐条读取，包括空闲记录。恢复会重新做只读模拟后才真正重放，这是为防止用户确认期间状态变化，不能直接删掉这层验证。

当前源码原生桥接库，在既有未安全退出镜像的副本上：

| 阶段 | 原始读取次数 | 不连续读取次数 | 读取字节 | 结果 |
| --- | ---: | ---: | ---: | --- |
| 初次研判 | 99 | 90 | 551,936 | 成功，0 写入 |
| 恢复及检查 | 21,058 | 10,702 | 24,337,896 | 成功，2 次写入，检查 9,982 项 |

20,324 次读取只有 1,024 字节。`RawPartitionIO` 使用原始设备，对每次请求分配对齐缓冲并单独读；此实验使用缓存中的普通文件，约 0.04 秒不代表实体 USB 机械盘耗时。不连续是相邻回调偏移不接续，不能直接当作每次都发生物理寻道。

证据：`.workbench/xhs-recovery-20261019/measure.py`、`native-read-counts.json`。仅副本被修改，原始夹具未修改。

修复方向：对 MFT 核验做受控的顺序分批读取/缓冲，保持损坏、空闲记录、序列号和分配核验语义；补阶段、读取量和耗时观测后，再在本地镜像与受控介质上比较。4TB 容量本身不足以推算时间，文件记录数量、历史分配、碎片和接口延迟均影响耗时。

## 3. 已复现：系统重新挂载失败仍返回恢复成功

`WindowsLogRecovery.swift:282` 丢弃 `diskutil mount` 的退出状态。若后台恢复成功但重新挂载失败/超时，`recover()` 仍返回成功，视图进入“已恢复，可以开启读写”。这与“修复成功”并非完全矛盾，但没有把未完成的挂载步骤告知用户。

使用真实 `WindowsLogRecoverer`，注入成功恢复和退出码 1 的挂载运行器，不执行任何系统命令，结果：

```json
{"mountFailureStillReportedAsRecoverySuccess": true}
```

证据：`.workbench/xhs-recovery-20261019/swift-probe/`、`swift-result.json`、`swift-build.log`。修复方向：分别保留恢复结果与挂载结果，展示“恢复完成，但未能挂载”的准确状态，而不是把已完成的磁盘恢复说成完全没恢复。

## 4. 已确认：30 分钟为前台等回复期限，并非后台停止期限

`HelperWindowsLogClient.timeout = 1800`；`HelperRPC` 到时结束等待并关闭连接，不会停止服务端的 `Task.detached` 原生工作。`WindowsLogRecoverer` 超时后因 `defer` 回到 `idle`，没有维护操作 ID/继续查询的协议。超时路径暂不重新挂载是正确的保护，但后续文案包含“仍然没有挂上时，拔下后重新插入”，没有先证明后台已经停止，需另行收紧。

隔离 Swift 探针确认 `timeoutReported=true` 且 `timeoutLeavesClientIdle=true`。服务端的设备锁仍有保护，不能据此声称实际发生并发写入；同样不能把前台超时当作后台已停止，或直接放开取消/强杀后台。

另外，卸载命令有最多 3 次重试，每次外部命令默认 5 分钟；恢复后还会等待重新挂载。窗口统一显示“正在补写并检查”，没有区分这些阶段。一个窗口等待时间并不等同于一次 30 分钟 RPC 的时间。

## 授权修复后的实施与验收

用户随后明确要求修复上述问题，本轮实现以下改动：

- 位图以 1 MiB 为单位读取，不再向原始设备请求超过 64 MiB 的连续传输；原始设备上限保留。
- 分配核验按约 64 KiB 一批读取 MFT，仍逐条执行原有校验；批次短读/错误时按单条回退判定，不跳过在用记录。独立评审进一步发现并修复旧代码对在用 BAAD 记录的漏检。
- Windows 日志恢复 RPC 的 30 分钟阈值变为慢响应通知；保留同一个请求继续等待，不再次执行修复、不虚报停止。其它 RPC 保持硬超时。
- 连接中断、无效回复等无法确认结果时，不挂载、不回到空闲，界面保留待核验并禁用相关操作。去掉该路径“未挂上就拔下重插”的建议。
- 后台处理成功而系统重新挂载失败时，返回独立挂载错误，显示“恢复完成，但未能挂载”，不触发后续开启读写。
- 界面区分暂时卸载、后台处理、长时间等待和重新挂载，显示已用时；恢复前说明耗时和取消限制。新增文案补齐简体、繁体和英文。
