# 符号链接与大文件验收（2026-09-29）

起因：小红书用户反馈“往移动硬盘备份 macOS 镜像文件时不行”，截图显示要备份的是“安装 macOS 27”和“安装 macOS Monterey”两个安装器应用。

## 复现

在主目录构建仿制安装器 `安装 macOS Test.app`：框架目录含 3 个符号链接（`Versions/Current → A` 等），`SharedSupport/SharedSupport.dmg` 为 16 GiB 随机数据。用 `ditto`（与 Finder 同走 copyfile）拷到 qsw（希捷 Expansion 2 TB，USB，NTFS）。

| 构建 | 结果 |
|---|---|
| 43（修复前） | 3 个符号链接全部 “Operation not supported”，Finder 遇到即中止整个拷贝；16 GiB 文件本身拷完，哈希一致，用时 1692 s，后段一度约 2 MB/s |
| 46（修复后） | `ditto` 返回 0；链接目标、类型与原目录一致；`find -type l`、`os.scandir` 均识别为链接 |

后段降速未复现：同一会话内 Python 顺序写 16 GiB 全程 14–16 MiB/s（平均 15.0），修复后 `ditto` 全程 1060 s（约 15.5 MiB/s）。首次降速发生在刚重启、系统负载很高时，判断为偶发。

## 修复

- 引擎：`nk_create_symlink` 并入 `create_node`，建 Interix 式链接（NTFS-3G 默认）：同名冲突返回 EEXIST 且不锁会话；继承父目录 Windows 权限；目标最长 1023 字节；创建后刷盘，失败按统一规则锁会话。Interix 链接的 `st_size` 报告为目标的 UTF-8 字节数。目录项 `nk_dirent` 末尾新增 `is_symlink`（取自 NTFS-3G 的 `NTFS_DT_LNK`）。
- 扩展：实现 `createSymbolicLink`，声明 `supportsSymbolicLinks`；目录枚举按 `is_symlink` 报告 `.symlink`。
- 选择 Interix 而非 Windows 原生链接：NTFS-3G 读取原生相对链接要按目标实际查找，目标尚不存在（拷贝时常见）就读不出。Interix 原样保存目标；macOS/Linux 为真链接，Windows 上是可复制备份的小系统文件、不跟随。
- 诊断报告版本号改读应用 Info.plist（此前固定为 “0.1.0-dev”）。

## 测试

- `scripts/test-ntfs-symlink.py` 3 项：框架式相对链接、中文目标、悬空链接、绝对路径链接读回一致，目录列表为链接；同名/超长/空目标拒绝且零写入、会话不锁；普通文件不误判、可删除、重挂载后仍在、卷干净。

- 已有问题（与本次无关，修改前即失败）：实验性 `test-ntfs-private-mode.py` 中 `ntfscat -a 0x50` 读取失败，另行处理。

## 未覆盖

- 硬链接仍不支持（与 exFAT 一致）。
- 写入吞吐约 15 MB/s，受每块写入前备份原内容（拔线可恢复）所限；对原为空闲空间的区域跳过备份可提速，但涉及恢复机制核心，需单独设计。
- 带 `restricted` 标记的系统自带应用（Safari 等）在 APFS/exFAT 上同样无法复制，属 macOS 保护。

## 追加：下载文件拷贝失败与“在 Mac 上检查”（同日）

用户补充：提示是“不能复制一个或多个文件”，没有接过 Windows、没有直接拔盘，手边没有 Windows 电脑。

### 下载文件拷贝失败

- 原因：下载来的文件带 `com.apple.metadata:kMDItemWhereFroms` 等扩展属性，名字含 `:`，而扩展属性存为 NTFS 命名数据流，流名不能含 `:`；引擎按文件名规则拒绝（EINVAL），`ditto`/Finder 因此整个文件失败，`cp -p` 数据拷过去但报错。
- 修复：属性名 `:` ↔ U+F022、`/` ↔ U+F026（Services for Macintosh 映射，Apple 与 Linux 的 SMB 客户端同用），列出时映射回原名；`\` 与 `$` 开头仍拒绝，拒绝在修改前、不锁会话。
- 测试：`scripts/test-ntfs-xattr-names.py` 3 项；qsw 实盘带下载属性文件 `cp -p`、`ditto` 均成功，属性原样保留。

### 在 Mac 上检查并清除“需要检查”标记

- 引擎 `nk_clear_check_marker`（`check_marker.inc`，仅后台组件编译）：只处理“单纯需要检查”；休眠、日志未安全关闭一律拒绝（可能有 Windows 未写完的数据）；只读遍历全部目录与文件记录并映射每个数据运行表，发现问题零写入；全部通过才清除 $Volume 的脏标志并复检为干净。不是 chkdsk。
- 后台组件新增请求 `clearCheckMarker`，与格式化共用核对（外接 USB、分区类型、未挂载、打开前后身份一致）；界面在只读提示旁加“在 Mac 上检查…”，确认框写明不等同 Windows 完整检查，完成后自动启用读写。
- 引擎测试 `scripts/test-ntfs-check-marker.py` 4 项：清除后卷干净、内容不变、ntfsfix 独立检查通过；未标记与只读描述符拒绝；记录损坏时镜像一字节不变；休眠文件拒绝。VolisleCore 新增 6 项（共 271）。
- 实盘：Windows 11 虚拟机 `fsutil dirty set` 后交回，盘屿预检为需要检查、保持只读。
  - 用 `mountvol /p` 干净离线后：命令行与界面各一次，检查 38 项后清除，自动恢复读写。
  - 用 `fsutil volume dismount` 后立即断开（Windows 很快重新挂载，相当于挂载中拔盘）：正确拒绝，提示回 Windows 安全弹出。
  - 用户验收发现按钮要点刷新才出现。原因：自动读写失败后，挂载流程的定期同步看到最近操作“已结束”，就清空了失败原因与那次操作，底部退回显示“尚未确认磁盘已经可读写”。修复：同步时若最近已结束的操作就是界面上那次且带失败原因，保留提示与操作，直到下一次操作开始（新增单元测试）；按钮目标改为直接取失败操作的分区名，是否已挂载改查实时挂载表，不依赖可能过时的磁盘列表。
  - 曾尝试在提示出现时自动刷新磁盘列表，但刷新会分配新的连接标识，使自动读写反复重试（3 分钟 37 次，均在只读预检被拒、无写入），已撤销；成功后也不再刷新列表。修复后 90 秒内只自动尝试 1 次，按钮无需刷新即出现，界面走完检查并恢复读写。
  - 恢复读写后底部仍残留“尚未确认磁盘已经可读写”：来自自动读写模块在插盘那次尝试里另记的笼统提示。新增 `AutoMountReported`：挂载流程已显示具体原因时，自动读写只消耗这次尝试、不再另记提示（新增单元测试）；检查成功后也清除它。读写状态下刷新按钮停用为既有设计。构建 52 由用户在界面完整验收：检查前显示“需要检查”与按钮，恢复读写后无残留提示。
