# 设备占用等待超时与迟到清理验收

日期：2026-09-25。

## 实现

原生设备占用等待现已使用 `RecoveryClaimWait`：每次系统请求默认等待 15 秒，取消或到期会向调用方返回错误；调用方停止等待后，不再允许该请求进入恢复操作。成功、原生拒绝、取消及到期共用单次完成状态，取消计时器，防止重复结束或迟到结果覆盖已返回的失败。

停止等待不代表系统已经取消请求。`NativeRecoveryDiskClaim` 保留尚未完成的原生回调上下文和对应系统会话，先尝试释放已经授予本会话的占用；若系统随后才返回成功，再释放该会话的迟到占用。最终回调到达后才注销回调、释放上下文和本地预约。没有提前释放 C 回调指针，也没有把迟到成功交给旧恢复操作。

`RecoveryClaimReservations` 按整盘媒体注册 ID 预约：正常占用、等待中的请求和已超时但回调未到达的请求均计入同一上限。进程内最多 16 个预约，同一整盘仅允许一个。迟到清理使用对应预约令牌，不能删除后来者的记录。若系统永远不答复，保留有界的待清理会话，拒绝继续堆积请求；没有假装回调已经完成。

Apple 开源实现中，释放磁盘占用会核对当前持有者是否属于发起释放的系统会话，见 [DAServer.c 的 `_DAServerDiskUnclaim`](https://github.com/apple-oss-distributions/DiskArbitration/blob/main/diskarbitrationd/DAServer.c)。本实现使用原请求自己的 `DADisk` 释放，并另用真实会话交接测试验证旧清理没有释放新的持有者；不能仅凭源码阅读推断所有系统版本均已实测。

## 验证

等待/预约专项 10 个测试入口、13 个参数化场景通过：即时成功、原生拒绝、等待取消、提交前已取消、到期后迟到成功、重复结果、截止时间边界、计时器清理、先清理再返回、同盘排他、总量限制和旧令牌不得释放新预约。

真实系统验收使用新建、只读挂接的 64 MiB NTFS 镜像。测试专用开关只延迟实际系统回调向状态机的交付，不伪造系统返回的成功/失败状态：

- 等待期限为 80 毫秒、交付延迟为 5 秒；调用在 1 秒内返回到期，恢复操作未执行，同盘新恢复请求被拒绝。
- 超时后让另一个独立 DA 会话取得设备占用，再等待旧会话清理；第三方竞争请求仍被新持有者拒绝，证明新持有者没有被旧清理解除占用。
- 另一笔请求已提交系统后取消，交付延迟为 2 秒；调用在 1 秒内返回取消，恢复操作未执行，同盘在清理前继续被拒绝。
- 两笔迟到回调清理完成后，待清理数量回到基线；新恢复作用域能够正常取得占用，退出后的旧对象无效。
- 先前完整占用生命周期回归也通过：真实竞争、挂载/推出拒绝、正常返回/抛错/取得占用后取消的释放，以及退出后正常只读挂载、卸载。

报告：`.workbench/native-claim-xlid6s8f/result.json`；两个系统测试入口均在同目录 `test.log` 中通过。镜像 SHA-256 未变，已正常分离；只删除本次新建成功镜像文件，保留证据。没有操作 qsw 或旧失败镜像。

核心回归报告 **210 个测试入口、24 组**，其中 208 个执行通过，2 个设备条件入口跳过；这两个入口已在上述真实镜像中单独执行通过。不要把跳过再计作一次系统验收。等待计时器测试使用主队列和真实时钟，没有以阻塞睡眠代替异步等待。

发布配置构建通过。以 `-c release -Xswiftc -enable-testing` 仅开启内部符号可见性后，正式物理入口的类型检查通过；测试镜像工厂、测试预约计数及待回调计数均明确报 `has no member`。回调延迟注入及其配置只在调试测试路径使用。该验证没有生成或安装新的 App 发行包。

## 边界

- 时限针对等待系统回调，要求主回调队列持续响应；它不能中断阻塞的系统 IPC，也不是对整段原始设备 I/O 的硬超时。
- 操作本身已经开始后的取消仍遵循操作方的协作取消；本轮验证的是等待阶段不得在取消/到期后开始恢复。
- 永不回调的真实系统服务故障、强制终止守护进程、热拔插、睡眠及多分区两级占用没有实测。没有为测试杀系统服务或强制分离磁盘。
- 回调迟到期间允许其他系统使用者接管；本地预约只阻止盘屿的新恢复请求，不是内核原始设备独占锁。
- 恢复工作线程、已持有原始设备描述符复核、生产大容量检查点、后台/FSKit 恢复接入及实盘验收仍未完成。

本轮未修改系统权限、已安装应用、官网或公开更新源；正式发布门禁保持阻断。
