# 在 Mac 上修复失效目录条目：评估（2026-10-10）

背景：用户 0.9.1“在 Mac 上检查”不通过，技术信息 `inconsistent record 194973: listed as a folder, record is a file`（见《当前交付清单》“用户反馈（2026-10-10）”）。本文回答：能不能在 Mac 上修、修哪几种、用 ntfs-3g 的哪些接口、怎样保证索引有序、每一步写入中断怎么还原、还有哪些风险。

状态（2026-10-10 更新）：第一步（诊断）已在本机编译并通过测试。所有者确认第 8 节四个问题都按建议做，第二步已实现（分支 `mac-repair-stale-entry`，未合并、未发布），验证情况见 [测试记录](../testing/2026-10-10-在Mac上修复失效目录条目.md)。

文中引用的 ntfs-3g 行为已对照上游 2026.7.7 标签源码核实（GitHub tuxera/ntfs-3g）：`ntfs_index_rm` 的三条路径（第 3 节）；目录排序为 `ntfs_names_full_collate(..., CASE_SENSITIVE, ...)`，即先不区分大小写、再区分；`ntfs_inode_open` 遇到未使用的记录返回 ENOENT（检查因此改为读记录头取序列号）；`ntfs_readdir` 先给出伪造的 “.” 和 “..”；挂载时 $MFTMirr 与 $MFT 前几条记录不一致会拒绝挂载（中途断开时用到）。

## 0. 第二步做了什么（按第 8 节的决定）

1. 记录已空闲、未被重用的失效条目一起修（第 2 节 B 类）。
2. 检查改严：每个索引项（含硬链接的第二个名字）都比对序列号，不一致即判失败，种类为 `stale entry, record reused` 或 `stale entry, record free`。用户那条报错在新版里会显示为前者（若两个序列号确实不同）。
3. 中断后还原：撤销记录写入卷序列号、分区大小和 Windows 日志开头 8 KiB 的 SHA-256。修复第一笔写入是“标记需要检查”（原本没有标记时），最后一笔才清除，所以中途断开的盘一定还标着需要检查（或读不出）。下次对这块盘做“在 Mac 上检查”或修复前，后台组件找到属于它的遗留撤销记录：仍标着需要检查（或读不出）且日志开头没变 → 原样回放；标记已清除（最后一笔已写）或日志开头变了（别处挂载过） → 改名留存、不回放；别的盘的记录 → 不动。补写日志功能的撤销记录没有写盘身份，不参与回放，行为不变。
4. 第一版只删叶子项、删后索引块不为空的条目；其余拒绝，交给 chkdsk。

## 1. 第一步已做的诊断

检查遍历到某个文件夹的索引项出问题时，技术信息在原句后追加所在文件夹的记录号和两个序列号（只有数字，不带文件名）：

```
inconsistent record 194973: listed as a folder, record is a file; folder 5021, entry seq 3, record seq 4
```

- `entry seq`：索引项里 MFT 引用的高 16 位（`MSEQNO(mref)`，ntfs-3g 的 `ntfs_readdir` 把整个 64 位引用传给回调）。
- `record seq`：该记录头里的 `sequence_number`。记录打不开时没有这一段。
- 两者**不同** ＝ 索引项指向的记录在条目写下之后被释放过（NTFS 释放记录时序列号加一），条目已失效；**相同** ＝ 同一个记录、类型却对不上，不是失效条目。
- 原来检查打开记录时只传记录号（`ntfs_inode_open(vol, MREF)`），ntfs-3g 不比对序列号，所以以前只能报“类型不符”，分不清这两种。
- 放宽：`CheckMarkerRefusal` 的正则只多接受 `; folder N, entry seq N(, record seq N)?` 这一个固定后缀，长度上限 120 → 160（最长实际 132）；桥接的 `discard_reason` 由 128 → 192 字节。调用方缓冲区放不下后缀时只回原句，不会截成半句（半句会被正则丢掉，用户就看不到技术信息）。
- 检查是否通过、何时写盘，行为不变：只多了文字。

改动文件：`packages/VolisleNTFS/bridge/check_marker.inc`、`ntfs_bridge.h`、`packages/VolisleCore/Sources/VolisleCore/HelperFormat.swift` 与其测试、`scripts/test-windows-log-recover.py`（结构体字段长度同步），新增 `scripts/ntfs_stale_entry_fixture.py`、`scripts/test-ntfs-stale-entry.py`（用镜像造出与用户相同的不一致，见第 7 节）。

**建议用户装上带诊断的构建后再跑一次“在 Mac 上检查”**，看到两个序列号再决定能不能对这块盘用第二步的修复。

## 2. 哪几种可以在 Mac 上修，哪些必须留给 chkdsk

| 情况 | 判据 | 处理 |
|---|---|---|
| A. 失效条目，记录已被别的文件或文件夹重用 | 序列号不同，记录在用 | **可修（第二步范围）**：只删这个索引项，附加前提见下 |
| B. 失效条目，记录已空闲、未被重用 | 序列号不同（或报 `listed but not in use`） | 技术上同法可修、风险更低（没有别的文件牵连）；**不在你限定的范围内，第二步是否顺带纳入请你定** |
| C. 序列号相同、类型不符 | 两个序列号相等 | chkdsk：可能是索引项里的重复信息过期，也可能是记录丢了文件夹标志或 `$INDEX_ROOT`，Mac 上分不清哪边对 |
| D. 索引项序列号为 0 | `entry seq 0` | chkdsk：无从判断是否失效 |
| E. 记录打不开、数据映射出卷、在用簇标为空闲、在用记录未分配、记录结构损坏、文件夹索引读不出（INDX 块撕裂、修复码不符） | 其余种类 | chkdsk |
| F. 同一块盘上 A 之外还有任何一处问题 | 全盘预扫描 | 整体拒绝，不做半套修复 |

A 的附加前提（任一不满足就拒绝，交给 chkdsk）：

1. **重用该记录的新文件必须能从它自己的上级文件夹正常找到**：读它的每个 `$FILE_NAME`，到所指上级文件夹的索引里查到同名、且引用的序列号与记录一致的项。否则说明丢失的那次索引写入把新文件的条目也一起丢了，新文件此刻只“挂”在失效条目上；删掉失效条目后它就成了没人发现的孤儿，我们的检查又看不见孤儿（只从根往下走），会让用户以为盘好了。chkdsk 会把这种文件放进 `found.000`。
2. **没有在用记录把失效条目指向的旧文件夹当作上级**（旧引用、旧序列号）。有的话是旧文件夹的子项没删干净，同样是孤儿问题。可在空间核对那一遍扫描所有记录时顺带查，不增加读盘次数。
3. **同一文件夹里指向这个旧引用的项全部一起删**：长名与 8.3 短名可能是两个索引项（检查遍历跳过 `FILE_NAME_DOS`，修复的收集阶段不能跳过），或一个 `WIN32_AND_DOS` 项。
4. **失效条目是叶子项**（无 `INDEX_ENTRY_NODE`），并且：在 `$INDEX_ROOT` 里，或在 INDX 块里且该块删后仍有别的项。见第 3 节。
5. 盘上失效条目总数有上限（建议 ≤ 8）；超过说明不是一次偶然丢失的写入，交给 chkdsk。
6. 休眠、Windows 维护未完成（`VOLUME_CHKDSK_UNDERWAY` 等）、日志不干净：一律拒绝（与现有检查同一套判断）。日志不干净的盘先走“补写日志”，补写后仍不一致才轮到修复。

“同一记录有没有被别的文件夹合法地当文件夹引用”：判据是序列号。合法引用的序列号一定等于记录当前序列号；我们只删序列号**不等于**当前值的项，所以不会删到合法引用。

### 现有检查的一个漏洞（建议第二步一起补）

检查用“已见过”位图避免硬链接重复检查：同一记录第二次被遇到时直接跳过，**不看类型也不看序列号**。所以：

- 如果遍历先经合法条目到达被重用的记录，之后再遇到失效条目，失效条目被静默跳过，检查通过并清除“需要检查”标记。镜像测试里就是这样：把新文件放在先被遍历的文件夹里，检查会通过（测试脚本特意把它放在后遍历的文件夹，才复现出用户的报错）。
- 失效条目指向的记录类型恰好一致（文件被文件重用）时，同样通过。

也就是说，现在“在 Mac 上检查”通过的盘上仍可能有失效条目。建议第二步把“序列号不同”本身定为检查失败，并对每个索引项（包括已见过的记录）都比对序列号（每个记录记一个 16 位序列号，100 万个记录约 2 MB 内存，不多读盘）。这会让检查更严：以前能清标记的个别盘会不再通过——那些盘本来就有 chkdsk 会修的问题，可接着用第二步的修复。**这是行为变化，请你确认。**

## 3. 用 ntfs-3g 的哪些接口删除失效索引项

只用目录索引这一层，**不用** `ntfs_delete` / `ntfs_unlink`：它们会改被指向的记录（删 `$FILE_NAME`、减链接数、释放记录与簇），而那个记录现在属于别的文件。

步骤（全部在后台组件的桥接里，文件名不出进程、不过 XPC）：

1. `ntfs_inode_open(vol, folder)` 打开所在文件夹；`ntfs_readdir` 收集该文件夹里引用等于失效引用（含序列号）的全部项及其名字和名字类型。
2. 对每一项：`ntfs_index_ctx_get(folder_ni, NTFS_INDEX_I30, 4)` → 用名字构造 `FILE_NAME_ATTR` 作键 → `ntfs_index_lookup(key, keylen, icx)`。
3. 删之前核对：`icx->entry->indexed_file` 与失效引用 64 位完全相等；`icx->entry->ie_flags` 不含 `INDEX_ENTRY_NODE`；在 INDX 块里时该块不止这一项。任一不符就停下，不写。
4. `ntfs_index_rm(icx)`；`ntfs_index_ctx_put(icx)`；最后 `ntfs_inode_close(folder_ni)` 把文件夹记录写回。

`ntfs_index_rm` 的三条路径（待核对 `index.c`）：

- 叶子项、在 `$INDEX_ROOT`：`ntfs_ie_delete` 把后面的项前移，`ntfs_ir_truncate` 缩短常驻属性。只改**文件夹自己的记录**（1 KiB）。
- 叶子项、在 INDX 块、块里还有别的项：`ntfs_ie_delete` 后 `ntfs_icx_ib_write` 写回**这一个 INDX 块**（通常 4 KiB，带多扇区修复码）。
- 非叶子项（`ntfs_index_rm_node`，用后继项替换、可能合并或释放子块、改索引位图）或块内唯一项（`ntfs_index_rm_leaf`，释放整块、改上级与位图、可能降层）：改动面大、ntfs-3g 这部分代码少有人走，**第一版一律拒绝**，交给 chkdsk。

因此一次修复的写入只有：每个失效项一个 INDX 块或文件夹记录，外加最后清“需要检查”标记的 `$Volume` 记录（及 `$MFTMirr` 里的副本）。第二步的故障注入测试会逐次数写入，若 ntfs-3g 比预想多写（比如顺带更新文件夹在上级里的重复信息），在测试里暴露并决定是否接受。

是否顺带更新文件夹的修改时间：不更新（少一次写入；chkdsk 不以此为错）。`$UsnJrnl` 里不会有这次改动的记录，与 ntfs-3g 平时写入一样。

## 4. 删除后怎样保证索引仍然有序

- 只删叶子项：同一个节点里后面的项整体前移，其余项相对次序不变；树的层数、子块指针、索引位图都不动。有序性由操作本身保证，不依赖重排。
- 删除前先核对该文件夹索引本来就有序（见下一条的核对方法）。本来就乱序的索引上 `ntfs_index_lookup` 可能定位错，直接拒绝。
- 删除后新增只读核对（第二步实现）：重新挂载，按 `ntfs_readdir` 的顺序逐对比较相邻项名字，用卷上的 `$UpCase` 与 ntfs-3g 的文件名排序规则（`ntfs_names_full_collate`，先不区分大小写、再区分）要求严格递增；项数恰好少了删掉的那几项，删掉的引用不再出现，其余项的引用与删前逐一相同。
- 然后跑全盘检查（含 `CHECK_ALLOCATION`）与第 2 节的孤儿核对；全部通过才清标记。
- 最终以 Windows `chkdsk`（只读，不带 `/f`）复核镜像为准，这一步只能在本机 Windows 虚拟机做。

## 5. 每一步写入中断时怎么还原

沿用补写日志的做法：`RawPartitionIO.undo` 在每次写入前把要覆盖的原内容追加进 `PartitionUndoLog` 并 `F_FULLFSYNC`；结果不通过就倒序写回、再核对原状。

| 中断点 | 盘上状态 | 还原 |
|---|---|---|
| 预扫描、核对阶段（只读） | 未写 | 无需还原 |
| 撤销记录写失败 | 未写（先存后写） | 直接报错 |
| 某个 INDX 块或文件夹记录写失败（返回错误） | 可能半写 | 同一进程内按撤销记录倒序写回，再跑只读检查确认回到原来的“检查不通过（同一条）”状态 |
| 删完、写后检查不通过 | 已改 | 同上，原样还原，向用户报“已还原” |
| 清标记写失败 | 条目已删、标记仍在 | 同上，整体还原（不留下“删了条目却没清标记”的中间态，便于说明） |
| **后台组件被杀、断电、拔线** | 任一中间态 | 现有机制**做不到**：撤销记录留在 `/private/var/db/volisle/windows-log-undo`，但没有任何代码在下次插盘时找它回放（补写日志功能也一样） |

最后一行是这次评估发现的缺口，需要你决定（2026-10-10：已决定补上，实现见第 0 节第 3 条）：

- 现状下的兜底：“需要检查”标记永远最后才清，所以中断后盘仍标着需要检查——盘屿不会读写挂载，Windows 下次挂载会自动跑 chkdsk。最坏情况是一个 INDX 块写了一半（修复码对不上），这个文件夹在 Windows 修好前读不出，chkdsk 会重建它的索引。写入总量只有几 KiB，窗口很小，但不是零。
- 建议补上（第二步内）：撤销记录头里记下卷序列号与分区大小；下次对同一卷做任何维护前，先发现遗留的撤销记录，经用户同意回放、核对后删除。回放本身也是写盘，同样要存撤销记录。这是新增的恢复路径，需要单独的故障注入测试。**范围是否包含它，请你定。**不包含的话，交付清单与界面文字都只写“同一进程内出错会还原”，不写“中断可还原”。

## 6. 你可能没想到的风险

1. **只看到第一处问题**：检查遇到第一处就停。丢失的那次索引写入可能还带来别的问题（比如应有的新条目缺失、新文件成了孤儿）。修复前必须全盘预扫描、收集全部问题，不能只修报出来的那一条。
2. **孤儿看不见**：检查只从根往下走，看不见没人引用的在用记录。修复若制造或掩盖孤儿，检查照样通过（第 2 节前提 1、2 就是为此）。
3. **其他系统索引里的旧引用**：被删的旧文件夹若有对象 ID（Windows 链接跟踪常给文件夹加）、重解析点或配额项，`$Extend\$ObjId`、`$Reparse`、`$Quota` 里可能还留着旧引用。我们的检查不看这些，chkdsk 会报。不影响读写，但意味着修复后 chkdsk 未必“完全干净”。验收时如实记录。
4. **`$Extend` 下的记录**：检查跳过记录号 < 24 的项，也就不进 `$Extend`；做孤儿核对时要把 `$Extend` 子树和扩展记录（`base_mft_record ≠ 0`）排除，否则会把它们误判成孤儿。
5. **排序规则依赖卷上的 `$UpCase`**：Windows 不同版本格式化的盘 `$UpCase` 不同，ntfs-3g 用卷上的那份。查找、核对都用它，不用内置表。
6. **非叶子项是常态**：大文件夹（几百项以上）里，被删项落在非叶子节点的概率不低。第一版会拒绝这类盘，实际能修的比例可能不高；先拿用户这块盘的诊断再说值不值得做第二版。
7. **用户期望**：修复不会“找回”任何东西——失效条目指向的那个旧文件夹在 Windows 上早已删掉；被重用的新文件原封不动，仍可从它自己的文件夹打开。界面要说清楚这是“删除一条已经打不开的条目”，不是恢复数据。
8. **USB 盒子的写缓存**：同步命令被盒子吞掉时，“写后检查通过”读到的可能是缓存。现有补写日志功能有同样的前提；实测过的两块盘没出问题，但不能保证所有盒子。
9. **超时**：修复 = 预扫描（全盘遍历 + 空间核对 + 孤儿核对）+ 写入 + 写后再全盘检查，约是现在检查的两倍多。大盘上要确认 1800 秒的超时够用，或拆成“研判”和“修复”两次调用（像补写日志那样先研判、给用户看、再执行）。
10. **只读研判与执行之间盘被改**：执行时必须重新研判，失效引用必须与研判时一致（像补写日志那样“App 的回答可能是几分钟前的”）。
11. **诊断本身的边界**：序列号回绕（65535 → 1）理论上可能让失效条目与新记录序列号碰巧相等，被归为 C 类而不修——只会更保守，不会误删。
12. **没有真实案例盘**：镜像造出来的是“最可能的成因”，用户盘上的真实成因没看到。在拿到用户的诊断输出（两个序列号）之前，不对外宣称支持。

- `HelperFormatTests`：新后缀接受、各种变形拒绝。

第二步（确认后）要加：

- 修复成功：只少了失效项，其余项、新文件内容、`/b/keep.txt` 不变；写后检查与有序核对通过；`ntfsfix -n` 与本机 Windows `chkdsk`（只读）复核。
- 拒绝：C、D 类，非叶子项，块内唯一项，新文件只挂在失效条目上（孤儿），休眠、维护未完成、日志不干净——全部零写入。
- INDX 块里的失效项：需要让 `/b` 的项多到长出 `$INDEX_ALLOCATION`，写回旧的 INDX 块（而非记录）。
- 故障注入：第 1…N 次写入分别失败（同一进程内还原后镜像逐字节等于修复前）；第 1…N 次写入后进程直接退出（`crash_after_write_at`），验证盘仍标“需要检查”、以及（若做第 5 节建议）遗留撤销记录能回放。
- 修复后 Windows chkdsk 复核干净：本机 Windows 虚拟机。

## 8. 需要你确认的事（2026-10-10 已确认：四项都按建议做）

1. 第二步是否把 B 类（记录已空闲、未被重用的失效条目）一起纳入。
2. 是否同时补检查漏洞：序列号不同即判检查失败、每个索引项都比对（第 2 节末）。
3. 是否在第二步内补“遗留撤销记录在下次插盘时回放”（第 5 节）；不补则对外只说“同一进程内出错会还原”。
4. 第一版只支持叶子项、不动 INDX 块结构，能修的比例可能有限——接受，还是先等用户这块盘的诊断再决定做不做第二步。
