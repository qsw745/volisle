# 自己发布新版本

一条命令完成：版本号、测试、构建签名、装到本机试用、苹果公证、更新目录、官网（含历史版本）、上线、打标签推送。

```bash
scripts/release/release.sh 0.6.2 ~/Desktop/notes.txt
```

脚本会在两个地方停下来问你，输入 `y` 才继续：

1. 新版本装到本机测试版（`~/Applications/Volisle Test.app`）之后：请插盘试一下读写、推出，没问题再继续。
2. 上线之前：确认后才会上传到官网；老用户随后会收到更新提示。

## 一、更新说明怎么写

纯文本文件。第一行是标题，后面每条以“· ”开头，**先写中文，再写英文**，条数可以不同：

```
盘屿 0.6.2 · Volisle 0.6.2

· 修复：……
· 新功能：……
· Fixes ……
· New: ……
```

这份说明会出现在三个地方：应用内的更新提示、官网中文更新日志（中文条目）、官网英文更新日志（英文条目）。写给普通用户看，说清楚“改了什么、对我有什么影响”。

## 二、第一次准备（这台 Mac 已经都准备好了）

换电脑或重装系统后，需要这些。具体的身份名、文件路径、密钥编号和服务器写在不入库的 `config/release.local.env` 里（格式见 `config/release.local.env.example`），这份文件请连同下面的密钥一起备份：

| 需要 | 在 release.local.env 里的名字 | 用途 |
|---|---|---|
| Xcode、Python 3、pnpm | — | 编译应用和官网；官网依赖在 `apps/web` 里运行一次 `pnpm install` |
| Developer ID 开发者证书（钥匙串） | `VOLISLE_SIGN_IDENTITY` | 给应用签名 |
| 带 FSKit 权限的描述文件 | `VOLISLE_PROFILE` | 文件系统扩展的权限 |
| App Store Connect API 密钥（.p8）、密钥编号、Issuer | `VOLISLE_NOTARY_KEY`、`VOLISLE_NOTARY_KEY_ID`、`VOLISLE_NOTARY_ISSUER` | 苹果公证 |
| 更新签名私钥（钥匙串，账户名 `top.qisw.volisle.updates`） | — | 给更新包签名。**丢了老用户就收不到更新**，请另外备份 |
| 服务器免密登录（`~/.ssh/config` 里的别名）与网站目录 | `VOLISLE_DEPLOY_HOST`、`VOLISLE_SITE_DIR`、`VOLISLE_RELEASES_DIR` | 上传官网 |

证书和公证密钥在 Apple Developer 网站可以重新生成；更新签名私钥不能重新生成，一定要备份。ntfs-3g 和 Sparkle 的源码由脚本自动下载到 `.workbench/`，不用手动准备。

脚本第一步会逐项检查以上条件，缺什么会直接告诉你。

## 三、脚本做了什么

1. **检查环境**：在 main 分支、没有未提交的改动、证书和密钥都在、能登录服务器、新版本号比当前大、更新说明格式正确。
2. **版本号与测试**：`config/updates.json` 版本号加一、构建号加一并提交；运行单元测试和本地化检查。
3. **构建签名**：构建、签名、装到本机测试版。核对扩展声明、各组件权限和后台组件配置与已发布版本完全一致；不一致就停止，因为原位升级后扩展会失效，用户要重新登录才能恢复。**这里停下来让你试用。**
4. **苹果公证**：应用和 DMG 都公证并装订。
5. **更新目录**：读回线上的更新目录（必须和仓库里的一致），生成新的、签好名的更新目录。
6. **官网**：上一版移入“历史版本”，下载页指向新版本，中英文更新日志加上本次说明；构建官网并暂存；历史版本的安装包和源码包从以前的发布目录拷贝，找不到就从官网下载，逐个核对 SHA-256。
7. **核对源码包**：源码包里的每个代码文件都要和发布提交完全一致（GPL 要求提供与安装包对应的源码）。
8. **上线**：预检服务器，提交官网改动。**这里停下来让你确认**，然后上传并切换，切换后逐个核对线上文件。
9. **标签与推送**：打标签 `v版本号`，推送到 GitHub。最后打印回滚命令。

## 四、中途出错怎么办

脚本遇到问题会停下并说明原因，不会带着错误继续往下走。

| 停在哪一步 | 状态 | 怎么处理 |
|---|---|---|
| 1 | 什么都没改 | 按提示补齐后重新运行 |
| 2～3（测试失败、构建失败、声明变化） | 只多了一个“版本号”提交 | 修好问题后，先撤销这个提交：`git reset --hard HEAD~1`，再重新运行 |
| 4～7 | 多了版本号提交和 `dist/Volisle-版本-build构建号/` 目录，官网没动 | 撤销版本号提交，删掉这个 dist 目录，重新运行 |
| 8 服务器预检失败 | 只多了版本号提交，官网没动 | 同上：撤销版本号提交，删掉 dist 目录 |
| 8 你选择不上线 | 多了两个提交（版本号、官网），官网没动 | `git reset --hard HEAD~2`，删掉 dist 目录 |
| 8 上传途中失败 | 部署脚本只有在全部上传并校验后才切换，官网仍是旧版 | 看提示；可以重新运行 `scripts/deploy-website.sh deploy …` |
| 9 推送失败 | 已上线，只是没推送 | 手动 `git push origin main v版本号` |

拿不准时，先别删任何东西，把终端输出发给我。

## 五、上线后发现问题

回到上一版（脚本最后会打印准确的命令）：

```bash
scripts/deploy-website.sh rollback 20261005-0.6.1-build64
```

回滚只影响官网和更新目录：还没更新的用户不会再收到新版。已经更新的用户需要再发一个修复版，不能让他们“降级”。

## 六、历史版本

官网下载页底部有“历史版本”，列出以前每个版本的安装包、源码包和 SHA-256，数据在 `apps/web/lib/history.ts`。发布脚本会自动把上一版移进去，不需要手动维护。服务器上的旧文件不会删除。

## 七、不要做的事

- 不要改 `apps/extension` 的 Info.plist 里的扩展声明，也不要改各组件的权限文件。脚本会拦住，但改之前先想清楚。
- 不要在 `dist/` 里手动替换安装包，官网上的哈希和更新目录签名都对应原来的文件。
- 不要跳过本机试用这一步。
