# 格式化与加密支持计划

日期：2026-09-28。所有者决定：格式化（整盘抹掉 + 单分区）都做；BitLocker 做到解锁并可读写；EFS 做导入 .pfx 后只读解密。测试盘：qsw 2 TB 可随意格式化（数据已备份）。三星 SSD 工作盘不参与任何测试。

## 调研结论

- **上游已有实现可参考**：盘屿引擎来自 whereteam/ntfskit（固定提交 b7153a8）。上游有 `nk_format`（NTFS-3G 的 mkntfs 快速格式化）、FSKit `startFormat` 接入（Info.plist 声明 `FSFormatOptionSyntax`）和 BitLocker 只读挂载；首轮接入时为控制风险刻意删除（见 `packages/VolisleNTFS/UPSTREAM.md`）。
- **格式化路径（实测后定稿，2026-09-28）**：
  1. `diskutil` 只认 `/System/Library/Filesystems` 里的格式，不认第三方 FSKit 模块。整盘先用 `diskutil partitionDisk diskN 1 GPT|MBR %Windows_NTFS% %noformat% 100%` 只写分区表（GPT Basic Data / MBR 0x07，不格式化不挂载；先格式化成 exFAT 会被 Spotlight 占住）。单分区不改类型，只允许本来就是 Windows 数据分区的分区。
  2. 写入 NTFS 由 root 后台组件直接完成：核对外接 USB、可写、未挂载、分区类型与 registryID，打开 `/dev/rdiskNsM` 后再核对一次，按块对齐读写，调用打过补丁的 mkntfs（`nk_format`），刷盘后只读复检。引擎（桥接层 + mkntfs + libntfs-3g）打成 `.workbench/format-engine/libvolisleformat.a`，只链接进后台组件；`nk_format` 用 `NK_WITH_FORMAT` 隔离，扩展和 App 主程序不含格式化代码。
- **为什么不用 FSKit 格式化（`startFormat` / `newfs_fskit`）**：
  - macOS 26.6 上，扩展声明 `FSFormatOptionSyntax` 且带 `shortOptions` 时，FSKit 会丢掉整个模块（系统设置里消失，读写也失效）；空的选项声明可以通过，但 `newfs_fskit` 就不接受任何参数（卷名传不进去）。27.2 没有这个问题。
  - 扩展声明（EXAppExtensionAttributes）一变，原位升级后 26.6 和 27.2 上扩展都会失效，直到重新登录或重启（fskit_agent 不重新读取声明；开关不会丢）。因此发布版必须保持与 0.3.3 相同的扩展声明。
  - 真实磁盘设备节点属于 root，普通用户调用 FSKit 格式化得到 EACCES；而 FSKit 模块按用户启用，纯 root 上下文找不到模块。
- **本地测试安装的坑**：暂存/回滚副本放在 `~/Applications` 里会出现多份同 ID 扩展，并可能重置扩展开关，安装脚本已改为放在 `~/Volisle 测试回滚副本`。虚拟机里反复安装不同声明的构建会让 fskit_agent 陷入找不到模块的状态，需重启虚拟机。
- **实测结果**：qsw 上 GPT 整盘、单分区、MBR 整盘各 4–10 秒完成（后台直接格式化，含中文卷名）；Windows 11 识别为健康 NTFS，只读 chkdsk 无问题，`fsutil volume allocationReport` 显示已用 158 MB；与 Windows 原生格式化的同尺寸盘相比，chkdsk 各项几乎一致；Windows 写入的文件回到 Mac 后自动读写、哈希一致。后台对已挂载分区、EFI 分区、整盘和非法卷名均拒绝。（Windows 核验用的是 FSKit 方案的产物，两种方案调用的是同一个 mkntfs 引擎。）
- **BitLocker**：上游用 libbde，只读，且许可证为 LGPL-3.0，与本项目 GPL v2 不兼容，不能直接使用。读写需自行实现或移植 dislocker（GPL-2.0-or-later，兼容）：密码 / 48 位恢复密钥 → VMK → FVEK，扇区加解密（Windows 10 起默认 AES-XTS；旧卷为 AES-CBC，可能带 Elephant 扩散器）。首版只接受“已完全加密”的卷，转换中、暂停、TPM 专用保护器一律拒绝。
- **EFS**：解密需要该 Windows 用户账户的证书私钥（导出为 .pfx）。NTFS-3G 的 ntfsdecrypt 同样要求 `-k key.pfx`。只读：RSA 私钥解出 FEK，再按 AES-256 / 3DES / DESX 解密数据流。

## 分阶段

| 阶段 | 内容 | 主要风险 | 验证 |
|---|---|---|---|
| 1 格式化 | 恢复 `nk_format` 与 FSKit `startFormat`；应用内“抹掉为 NTFS”（整盘：新建 GPT 或 MBR + 单个 NTFS 分区；单分区：格式化选中分区）；输入盘名确认；仅外接 USB，拒绝系统盘、内置盘和 /Volumes/Data 所在盘；完成后自动检查并开启读写 | 误选磁盘；分区类型不对导致 Windows 不认 | 镜像 → qsw 实盘；Windows 11 虚拟机核对可读写、chkdsk 无错误 |
| 2 EFS 只读 | 导入 .pfx（仅存钥匙串，扩展通过共享访问组读取）；识别 EFS 文件并只读解密；无证书时保持现状 | 私钥保存与沙盒访问；解密算法兼容 | Windows 虚拟机生成 EFS 文件与 .pfx；逐字节比对 |
| 3 BitLocker 只读 | 识别 `-FVE-FS-`；输入密码或恢复密钥解锁；解密层接在块 I/O 之下；只读挂载 | 密钥派生与元数据解析；偏移重定向（卷头与备份区） | Windows 虚拟机生成 BitLocker 卷（XTS 与 CBC 各一）；逐字节比对 |
| 4 BitLocker 读写 | 写入时加密；解密层置于写入日志与拔线恢复之下，日志记录密文块；重新跑中断矩阵与拔线测试 | 与恢复机制耦合，风险最高 | 镜像逐点故障矩阵 + qsw 物理拔线 + Windows 往返 |

每阶段单独发布（0.4.x），官网兼容性表只写实际验证过的范围。

## 需要的外部条件

- BitLocker 与 EFS 测试数据需要 Windows 专业版：Windows 11 虚拟机需确认版本；家庭版只能解锁，不能新建 BitLocker 或 EFS。
- dislocker 源码作为参考需下载（GitHub，GPL-2.0-or-later），下载前核对许可证与固定提交。

## BitLocker 只读：实际设计（2026-09-30）

- 解密层自写（`packages/VolisleNTFS/bridge/bitlocker.inc`，依据 libyal 公开的格式说明，加解密用系统 CommonCrypto），未使用 libbde 或 dislocker 代码。支持 Windows 7 起的完全加密卷：AES-XTS 128/256、AES-CBC 128/256；拒绝 Vista 格式、Elephant 扩散器、转换中或暂停的卷、只有 TPM 保护器的卷。
- 钥匙交接：沙盒扩展读不到用户输入，也不能随意与后台组件通信。做法是后台组件（root）核对分区（外接 USB、Windows 数据分区、未挂载、打开前后身份一致）后只读打开原始分区，用密码或恢复密钥解出卷主密钥（VMK），再以用户身份执行 `mount -F -t volisle -o rdonly,…,volisle-bde=<VMK>`；扩展用 VMK 解开卷密钥（CCM 校验，错一位即拒绝）并只读挂载。扩展看不到用户密码；VMK 不写日志、不落盘。
- 已知取舍：VMK 在 `mount` 命令运行的一两秒内出现在进程参数中，本机其他进程在这段时间可以看到。它只能配合这块盘的密文使用；而同一时刻本机进程本来就能读取已解锁卷里的文件。若以后要消除，可改为经应用组容器交接（需改扩展权限，扩展声明不变）。
- macOS 不为 BitLocker 分区自动挂载（系统认不出文件系统；盘屿扩展未声明介质类型，系统插盘时不会用它探测）。应用把“系统认不出文件系统的外接 Windows 数据分区”列为候选，由后台组件逐个确认是否 BitLocker；已解锁状态取自实时挂载表（系统磁盘服务不跟踪这类挂载）。
