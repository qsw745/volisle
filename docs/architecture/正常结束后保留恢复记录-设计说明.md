# 正常结束后保留恢复记录：设计说明（方案 A）

起草：2026-10-11。状态：所有者 2026-10-11 审阅通过（续接、30 天过期、回滚提示与拷贝确认并入 D），在分支 `clean-end-retention` 上实现。范围：扩展里的写入日志（`WriteJournal*.swift`、`NTFSVolume.swift` 的会话收尾）。方案 C（已损坏盘的受控处理）和 D（界面提示）只在第九节说明与本方案的衔接，各自另行说明。

## 一、问题

2026-10-11 实盘：0.9.2 对 qsw 2 TB（Seagate Expansion，USB）的读写会话在 14:27:54.920 “正常结束：记录已清除”，1.1 秒后被直接拔线（没有推出）。重插后 `$MFTMirr does not match $MFT (record 3)`，预检返回 4，盘屿无法以读写打开。

原因有两层：

1. FSKit 的 `metadataFlush` 只把数据交给硬盘，不让硬盘把自己的缓存写到盘片上。证据：拔线时内核 USB 存储驱动的统计行里，这次 16 分钟的连接从未发过缓存同步命令（`SyC:0`），最后一次写在拔线前 1096 毫秒；同一块盘被“推出”的那几次连接都发过。
2. 运行期间我们知道这一点，所以已确认的批次再保留 20 秒（`WriteJournalLimits.retentionSeconds`），断电后回滚整个窗口。但 `WriteJournalCoordinator.finish` 在最终检查点刷新之后立刻 `removeAll`，把窗口内的批次连同最终批次一起删了。会话一结束，保护归零。

实盘读数（所有者用 `scripts/ntfs_mirror_records.py` 只读读出）：记录 0–2 两份一致；记录 3 的 `$MFT` 那份（偏移 19456）是清掉标记的新版本，更新序号 10；`$MFTMirr` 那份（偏移约 1 TB）仍带脏标记，更新序号 9；两份都没有撕裂，差异只有 4 个字节（更新序号、脏标记位、两处扇区校正）。也就是相距约 1 TB 的两处写入，硬盘只写出了近的那一处。

镜像复现（`python3 scripts/test-write-journal.py --finish-loss`；修复前 10 种丢失情形 9 种不满足“下次能打开、内容一致、能再写”）说明后果不止记录 3：

| 丢了什么 | 下次连接看到的 |
|---|---|
| 清标记的两处写入丢一处 | 记录 3 不一致，预检 4，打不开（实盘症状） |
| 两处都丢，或窗口内写入全丢 | 一致但带脏标记，预检 1，“在 Mac 上检查”可处理 |
| 结束前的操作里丢一个目录索引块 | **看似干净**（预检 0、镜像一致、`ntfsfix -n` 通过），根目录索引损坏，下一次写会话失败 |
| 标记落盘、其余块丢一半 | 看似干净且能再写，新文件全部列不出 |

后两种没有任何信号，盘屿会在不一致的卷上继续读写。只有保留记录才能发现并撤销，所以 A 是修复本身，C 只是善后。

## 二、目标与不做的事

目标：

1. 正常结束后，窗口内任何一部分写入没落到盘片上，下次以读写连接时都回到最早保留点的一致状态，与会话中途拔线的结果相同。
2. 绝不回滚别人的改动（Windows、另一台 Mac、本机另一个版本的盘屿、后台组件的检查与修复）。
3. 正常结束的盘不会因为留下的记录而被拒绝读写。记录在这里只是保险，判断不了就丢弃记录、按盘的现状处理，等同今天的行为。
4. 本机占用和下次连接的耗时都有上限。
5. 降级到旧版本时，旧版本的行为与今天完全一样。

不做：

- 不保证硬盘缓存超过 20 秒仍未写出的情形。这是运行期窗口已有的假设，本方案沿用，不加强。
- 不改会话中途的检查点、批次格式和回滚算法。
- 不处理没有记录可用的盘（已经坏了的盘、旧版本留下的盘），那是方案 C。

## 三、现状（供对照）

正常结束的顺序，`closeEngine` → `nk_umount` → `finish`：

1. 引擎写出待写元数据，再清脏标记（`$MFT` 记录 3 和 `$MFTMirr` 记录 3 所在的两个缓存块）。这些写入只进会话的内存层。
2. 最终检查点：先把被覆盖的旧内容记到本机并落盘，再把块交给系统缓存，`metadataFlush`，写检查点记录。
3. 再 `metadataFlush` 一次，然后 `removeAll`：先删会话记录，再删全部批次。

顺序没有问题，问题只在第 3 步删得太早。

下次连接：`recoverInterruptedWrites` 只在以读写激活时运行。找不到会话记录就什么都不做。

## 四、设计概要

**保留窗口不再随会话结束而结束。** 正常结束只是在这条批次链上做一个“已结束”的记号；批次仍然只在两种情况下删除：超过窗口并确认落盘，或在下次连接时处理完毕。

三处改动：

1. `finish`：不删批次，把会话记录换成“已结束记录”。
2. `recover`：遇到已结束记录时，逐块判断属于“都落盘了 / 自己丢了写入 / 别人改过”，分别处理。
3. `begin`：遇到“都落盘了但还在窗口内”的已结束记录时，接着这条链继续写，不等待。

## 五、本机记录

### 5.1 新文件 `<序列号>.finished`

内容是原会话记录（结构不变）加结束信息，同样带校验码（域标签 `finished|`）：

| 字段 | 用途 |
|---|---|
| 原会话记录 | 会话标识、引导扇区、开始时的卷标志、`$LogFile` 位置与摘要 |
| `firstEpoch`、`lastEpoch` | 结束时仍保留的批次范围；用来确认批次集合完整 |
| `finishedUptime` | 结束时的开机时长（与窗口同一个时钟，不含睡眠） |
| `finishedWall` | 结束时的日期，只用于过期清理 |

批次文件不变，仍按会话标识校验。

### 5.2 为什么用新文件而不是给会话记录加一个状态

旧版本读到不认识的状态会判为记录损坏，从此拒绝读写这块盘；改成提高版本号则判为格式不支持，同样拒绝。换文件名后旧版本根本看不到已结束记录，开始新会话时会把没有会话记录的批次当作残留删掉（已有逻辑），行为与今天完全一样。

### 5.3 写入顺序与中断

结束时：先写 `.finished`（临时文件、落盘、改名、目录落盘），再删 `.session`（目录落盘）。两步之间中断会同时留下两个文件，按下表处理：

| 本机上有什么 | 含义 | 处理 |
|---|---|---|
| 只有 `.session` | 会话中断，或上次恢复待确认 | 现有逻辑，不变 |
| 只有 `.finished` | 正常结束 | 第七节 |
| 两个都有，会话标识相同，`.session` 为进行中 | 结束、续接或回滚开始时在两步之间中断；此时没有任何新写入 | 当作已结束，补删 `.session` |
| 两个都有，会话标识相同，`.session` 为已恢复 | 正常流程不会产生（回滚前已删 `.finished`） | 以 `.session` 为准，删 `.finished` |
| 两个都有，会话标识不同 | `.finished` 是降级期间留下的旧记录 | 删 `.finished`，按 `.session` 处理 |
| 有 `.finished` 但批次不全（缺号、有未确认的批次、校验不过） | 被旧版本清理过，或本机文件损坏 | 不回滚，删掉这组记录，按盘的现状处理 |

最后一行是硬规则：**回滚要么用完整的保留批次，要么不回滚。** 只用一部分批次回滚会把较新的数据盖回旧内容，这正是现有代码坚持“最旧的先删、删除先落盘”的原因。

### 5.4 过期与占用

- 每次打开记录目录时，删除 `finishedWall` 早于 30 天的已结束记录及其批次。它们只是保险，删了等同今天的行为。
- 单卷占用上限不变：窗口内批次最多 128 MiB，最终批次通常在 32 MiB 以内、硬上限 256 MiB。常见情形（拷到空闲空间）只有几十 KiB，因为写到空闲簇不保存旧内容。
- 作废归档（`archive`）把 `.finished` 一并移走。

## 六、结束流程（`finish`）

1. `session.retention = ∞`，最终检查点，`metadataFlush`。与现在相同，保证收尾期间不删任何批次。
2. 写 `.finished`：批次范围取会话当前保留的批次加最终批次，`finishedUptime` 取当前时钟。
3. 删 `.session`。
4. 日志改为“写入日志会话正常结束：记录保留到确认写入”。

任何一步失败都不删任何东西并返回失败，记录仍是进行中的会话，下次连接按中断恢复。这与现在“结束失败则记录保留”的行为一致，只是多了一个可能失败的写文件步骤。

卸载耗时：原来是删文件加两次目录落盘，现在是写一个小文件加两次目录落盘，基本不变。

## 七、下次连接（`recover` 遇到已结束记录）

仍然只在以读写激活时运行，仍然先拿卷的记录锁。只读挂载不碰记录。

### 7.1 先判断是不是同一个卷的同一个状态

沿用现有两项检查：设备大小、块大小、引导扇区与记录一致；`$LogFile` 开头的摘要与记录一致。任何一项不符说明在别处用过。

处理：删掉这组记录，返回“无事可做”，由随后的只读预检按盘的现状决定。不拒绝、不归档。这与现有“已恢复的记录遇到日志变化”的处理相同。读不出来的 `.finished`（损坏或更新的格式）同样处理。

BitLocker 卷没有密钥时读不了卷内容，保持现状（返回不可用，记录不动）。

### 7.2 逐块分类

读出保留批次里记过的每个块，按批次里的信息分三类：

- **已落盘**：内容等于这个块最后一次写入的摘要。
- **自己的旧内容**：等于记录里更早的某个版本，或按扇区看是新旧版本的拼合（现有 `verify` 的逐扇区判断）。这是丢在硬盘缓存里的写入。
- **别人的内容**：以上都不是。

没有保存旧内容的块（写入时是空闲簇）只能判断“已落盘 / 没落盘”，没落盘算作丢失，不参与“别人的内容”的判断。

读盘量有上限：保存了旧内容的块全部读（受保留预算约束，最多几百 MiB）；写到空闲簇的块只读最新的 256 MiB（`landingFreeBytes`），更早的不读。硬盘自身的写缓存不超过这个量，它还可能攥着没写出的只会是最新的这些。所有块按设备偏移排序、相邻的合并成一次读。结束前刚拷过几 GB 的大文件时，不设上限、逐块乱序读会让下次激活多出几分钟。

结论按这个顺序取第一个成立的：

| 结论 | 条件 | 处理 |
|---|---|---|
| 别人改过 | 有任何一块是别人的内容 | 不写盘，删记录，按盘的现状处理 |
| 自己丢了写入 | 有任何一块没落盘 | 回滚（7.3） |
| 都落盘了 | 全部已落盘 | 看是否过了窗口（7.4） |

“别人改过”优先于“自己丢了写入”，宁可不回滚。

为什么能认出别人：任何把卷标为使用中的写入方都会改写 `$Volume` 记录，而记录 3 所在的两个块一定在最终批次里并且保存了旧内容；NTFS 记录每写一次更新序号加一，所以改写后的内容不会等于我们记过的任何版本。Windows 另外还会被 7.1 的日志检查挡住。后台组件的“在 Mac 上检查”和失效条目修复也改写记录 3，同样被认出。

认不出的情形：有工具绕过文件系统直接改了保留批次以外的块，同时我们自己又丢了写入。这时只把批次里的块恢复到 20 秒内的旧内容，那些外部改动不受影响。不再设防。

### 7.3 回滚

先把 `.finished` 换回进行中的 `.session`（先写后删，都落盘），然后才有第一笔盘上写入。从这一刻起它就是一次普通的中断会话，走现有的同一段代码：核对、批次从新到旧写回旧内容、释放本机脏标记、只读预检必须干净；激活阶段没有持久刷新时把记录存为“已恢复”，等之后的刷新确认再删。回滚中途再次中断也走现有路径，不需要新的状态。

回滚后预检仍不干净时，与中断恢复一样拒绝读写并保留记录。这说明丢失超出了窗口，我们无法担保。

日志单独一条：“上次正常结束后过早断开，最近的改动没有写到盘上，已回到之前的一致状态”，让用户的反馈能和中断恢复区分开。是否在界面上提示见第九节。

### 7.4 都落盘了：能不能删记录

读回来的内容可能还只在硬盘缓存里（盘没断过电），所以“都落盘了”还不够，要过了窗口才算数：

- 当前开机时长小于 `finishedUptime`：重启过，算过了窗口。
- 当前开机时长减 `finishedUptime` 不小于 20 秒：过了窗口。
- 否则：还在窗口内。

过了窗口：删记录，返回“无事可做”。没有任何盘上写入。

还在窗口内：记录不动，返回“无事可做”，并在这个卷实例里记下“本次激活已核对过”。之后只读使用、然后被拔线，记录还在，下次连接重新判断。之后要写，见第八节。

## 八、窗口内再次写入（`begin`）

`begin` 在第一次改动时运行，此时已有持久刷新。遇到已结束记录：

| 情形 | 处理 |
|---|---|
| 本次激活核对过，现在已过窗口 | 删记录，开新会话（现有路径） |
| 本次激活核对过，仍在窗口内 | 续接（见下） |
| 本次激活没核对过（不应出现） | 拒绝写入，与现在遇到意外记录时相同 |

第一种情形不用重新读盘：从激活到现在盘一直挂着没断过电，激活时读到的就是硬盘缓存里的内容，过了窗口即视为已写出。

**续接**：用同一个会话标识和记录重新开始，批次号从 `lastEpoch + 1` 起；把留下的批次装进会话的保留列表，时间都记为 `finishedUptime`（比各自的实际时间晚，偏保守）；把 `.finished` 换回 `.session`。之后这些批次由现有的 `pruneRetained` 按时间从旧到新删除。

接管记录的时机：不在续接开始时，而是推迟到第一批新写入即将记录之前。先写 `.session`，再删 `.finished` 并落盘，然后才记这一批。这样一次没写成的续接（例如可写引擎没打开）留下的仍是原样的已结束记录，下次连接重新判断；如果一开始就换文件，这种情形会留下一个进行中的会话，下次连接把上一次早已落盘的内容白白回滚掉。两步之间中断时还没有任何新写入，按 5.3 表第三行当作已结束是对的。

续接前会再核对一次卷的引导扇区、标志和日志摘要与记录一致、批次完整。不一致时不拒绝写入，而是删掉记录开新会话，等同今天的行为。

续接期间的保守处理：装进来的批次不带簇位图快照，按“位图未知”对待，于是在它们被删掉之前，新写入一律保存旧内容，不走空闲簇的省略。最多持续 20 秒。

续接后中途拔线：现有恢复把新旧批次整条链回滚到最早保留点。那一点可能在上一次挂载里，卷标志是“开始标志加脏标记”，现有的释放标记逻辑已经处理这种情形。

为什么不用等待代替续接：等待要在持有操作锁的情况下睡最多 20 秒，期间这个卷的读操作也全部卡住；放到激活阶段等则让挂载慢 20 秒，磁盘仲裁的超时行为没有把握。续接没有时间依赖，代价是改动落在会话构造上。

## 九、与 C、D 以及应用的衔接

- **方案 C**：处理没有可用记录的盘，例如旧版本留下的盘、记录过期后才出现的盘。A 上线后同样的损坏应当不再产生，但 C 仍然需要。C 写盘时会改写记录 3，A 会认出是别人改过并丢弃记录，两者不冲突。分支 `volume-mark-copies`，见 [测试记录](../testing/2026-10-11-检查标记只写到一处.md)。
- **方案 D**（分支 `unplug-ui`，基于本分支，2026-10-12 实现）：
  - **提示推出**：写会话结束后的底栏提示改为“磁盘已恢复只读。硬盘可能还在写入最后的内容，请先推出，再拔下数据线。”系统的推出会发缓存同步命令，是唯一确定的落盘手段。
  - **回滚提示**：扩展在挂载根目录上多应答一个只读的虚拟属性 `top.qisw.volisle.recovery`（本次激活回滚过一个正常结束的会话时值为 `after-end`，否则不存在）。应用开启读写时读它，底栏说明上次没有推出就拔下、最后一小段时间的改动没有写到盘上、已恢复到之前的一致状态，请检查最近拷入或修改的文件。
  - **拷贝确认**：会话干净结束不再立即把其中拷完的任务标为已确认。之后分三种情形：
    - 磁盘继续连着满 25 秒（按开机时长）：确认。
    - 经盘屿推出（推出前记下，磁盘随后消失）：确认。只认会话结束之后发起、并且没有被系统拒绝的推出；更早的推出、被拒绝的推出都不能为之后的拔线作保。
    - 磁盘一直连着、25 秒内又开了读写：不复查，照样等满 25 秒确认。
    - 25 秒内磁盘不见了、又不是经盘屿推出的：按可能被回滚处理，任务回到“等这块盘”，下次可写时复查补齐。这与会话非干净结束时的现有处理相同。
  - 回滚提示每个写会话只说一次；经盘屿推出成功后，“请先推出”的提示随之清掉。
  - 独立代码审查（2026-10-12）提出的四条意见已处理（上面两条规则、回滚提示重复、多余的定时任务）。
  - **已知的不足**：在访达里推出（不是经盘屿）且发生在结束后 25 秒内时，应用分不出推出和直接拔线，任务会显示为等待，下次接上并可写时复查后完成。应用在这 25 秒内被退出时，任务停在“正在确认写入”，同样到下次可写时复查。

## 十、对拔线恢复路径的影响与风险

| 风险 | 说明 | 对策 |
|---|---|---|
| 把别人的改动回滚掉 | 这是最坏的结果 | “别人改过”优先；批次不全不回滚；专门的用例：另一台 Mac 的盘屿、后台组件检查、Windows、只改了日志开头 |
| 用户在正常结束前 20 秒内做的事被回滚 | 只在确实丢了写入时发生，另一种结局是卷损坏 | 单独的日志；界面提示（D） |
| 正常结束的盘被拒绝读写 | 只可能出现在回滚后预检仍不干净时 | 与中断恢复同一处理；其余无法判断的情形一律丢弃记录 |
| 续接改动了会话构造 | 落在最敏感的代码上 | 续接后的每个设备写入点都进故障矩阵；续接逻辑单独一个提交，便于回退到“不续接、拒绝窗口内写入”的简化版 |
| 中断恢复本身被改坏 | 分类和回滚与现有恢复共用代码 | 只读分类单独成函数，现有 `verify` 的行为和全部现有用例不变 |
| 降级 | 旧版本看不到新文件 | 用旧源码构建的驱动对着新记录目录跑一遍 |

没有改动的部分：批次文件格式、检查点、运行期保留窗口、回滚顺序、释放标记的条件、桥接层。
