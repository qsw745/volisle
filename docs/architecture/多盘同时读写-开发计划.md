# 多盘同时读写与“拷完精确确认”开发计划

起草：2026-10-08。状态：计划，未开工。起因：GitHub issue #1 报告者建议多盘同时读写；所有者决定进入下一阶段开发（此前 2026-09-27 的决定是“同一时间一块盘”，原因是后台组件按单操作设计、手上没有第二块 NTFS 盘）。

## 一、现状结论

“一次只能写一块盘”不是 FSKit 的限制，也基本不在扩展里，而是 App 与后台组件（helper）两层写死的：

| 层 | 现状 | 结论 |
|---|---|---|
| 扩展 | `UnaryFileSystemExtension`，每块盘一个独立进程；引擎队列、写入日志、检查点计时器都是实例成员；日志文件按卷序列号命名，跨进程用 `flock` 互斥 | 已经能并行，只需小改（见第三节阶段 1） |
| helper | `HelperMountCycleService` 只有一个 `operation` 与全局 `working`（`HelperMountCycle.swift:72-83, 129`）；记录是唯一的 `/private/var/db/volisle/operation.json`；`latest` 只返回一条；`HelperDiskInspector` 全局 `lock.try()`（`SystemFSKitMount.swift:298`） | 要改成按操作 ID 的多条记录 |
| App / Core | `DeviceOperationGate` 的 barrier 是全局的，写会话期间一直持有，冻结所有盘的操作（`DeviceOperationGate.swift:18, 47`）；`MountCycleClient` 的 operation/intent/barrier/writableURL 全是单值；intent 只有一个文件 `pending-readonly-check.json`；`CopyQueue.sessionEnding` 是全局布尔，结束 A 盘会话会停掉 B 盘的拷贝；界面上 `writeHolder`/`WriteSlotWait`、底部栏唯一的“恢复只读” | 主要工作量在这里 |

已有的并发先例：BitLocker 盘可与普通盘同时写（0.6.0），但它是绕开挂载周期做的（无持久 intent、无自动读写、无拷贝队列、无会话健康检查），不能照搬，只能参考它“按分区记状态”的做法。

扩展与 App 之间没有 IPC；唯一的实时通道是挂载根目录上的虚拟扩展属性（`top.qisw.volisle.write-state`、`mount-mode`，`NTFSVolume.swift:1239-1301`），按挂载点区分，扩展退出后自动失效。新的确认信号沿用这条通道。

## 二、拷完精确确认（先做，独立可发）

现在拷完固定等 60 秒才显示“打开文件”（`CopyQueue.confirmAfter`）。真正的条件是：这次拷贝最后一批写入所在的日志周期已检查点、且它及更早的周期记录都已被持久删除（超过 20 秒保留窗口），此后拔线不会再回滚它。正常 22–30 秒，慢盘更久；而删除失败时固定 60 秒并不可靠。

做法：

1. 扩展新增只读虚拟属性 `top.qisw.volisle.durability`，值为一行文本：`v1 session=<会话 UUID> written=<最近写入的周期号> durable=<已不可回滚的最大周期号>`。
   - `WriteJournalSession.write()` 记录 `lastWriteEpoch`；`RetainedEpoch` 加 `epoch` 字段；`checkpoint()` 与 `pruneRetained()` 更新快照。
   - 快照用独立小锁，应答属性时不进 `operationLock`/`engineQueue`，长时间写入期间也能读。
   - 与 `write-state` 一样禁止写入、只在根目录应答。
2. App：拷贝完成时读一次记下 `session` 与 `written`；之后随现有会话检查节奏轮询，`durable ≥ written` 且会话未变即确认。
   - 读到 `stopped`、会话变了或盘不在：沿用现有逻辑（干净结束则确认，否则复查补齐）。
   - 旧扩展没有这个属性（ENOATTR）：退回固定 60 秒。
   - 界面文字改为“正在确认写入…”，不再写“约 1 分钟”。
3. 验收：故障矩阵加“确认前/确认后拔线”两类；实盘 qsw 上拷完立即拔、确认后立即拔各若干次，确认后拔的文件必须完整。

这一项不依赖多盘，可以先单独发版；多盘阶段每块盘各读自己挂载点上的属性，天然适用。

## 三、多盘同时读写分阶段

上限先定为 **2 块**普通 NTFS 盘（另加已解锁的 BitLocker 盘照旧）。每阶段结束都要能单独构建、全量测试通过，单盘行为不变。

### 阶段 1：扩展小改
- `WriteJournalStore.archive()` 的归档保留数按卷序列号各留 3 份（现在是全局 `dropLast(keep)`，A 盘会挤掉 B 盘的归档）。
- 文档写明“一卷一进程”前提（`NTFSVolume.swift:597` 的 `exit(0)`、`names.inc` 的进程级全局量依赖它）。
- 克隆盘（序列号相同）的检测挪到阶段 2：App 拿不到 NTFS 序列号，helper 开始读写前读引导扇区时顺带取出，拒绝同号的第二个会话并说明原因。扩展层已有兜底：同号第二个会话拿不到日志锁，只能只读。

### 阶段 2：helper 多会话（风险最高）
- `operation` → `[UUID: HelperMountOperation]`，`working` → 按盘的集合；`start` 只拒绝同一块盘（同 deviceGroup）上未结束的记录，加并发上限。
- 记录文件 `operation.json` → `operations/<uuid>.json`，兼容迁移旧文件；崩溃后启动时逐条标记 needsRecovery，收据按全部当前记录保留。
- 新增 `list` 动作返回该用户全部未结束记录；放宽回复大小上限（`HelperProtocol.swift:126` 8 KiB 与 `HelperMountRPC.swift:42` 16 KiB 不一致）。
- `HelperDiskInspector` 改为按设备加锁。
- 检查报告带上 NTFS 卷序列号；已有同号盘在写时拒绝第二块（克隆盘）。
- `quiesce`（更新前）要求所有记录都已结束。
- 维护引擎（mkntfs、清标记、Windows 日志）的全局锁保留，并明确与挂载流程的互斥。

### 阶段 3：Core 客户端多会话
- `DeviceOperationGate`：写会话持有按设备的 barrier；全局 barrier 只留给应用更新与“请求结果未知”的 intent。
- `MountCycleClient`：拆成按会话的子状态（`[UUID: Session]`），`recover`、`checkWriteSession`、`prepareForEject`、`isWritable`、`verifiedWritableURL` 都带盘或会话参数；`refresh` 用 `list` 对账。
- intent 存储：按 intent ID 一个文件，`loadAll`；兼容读取旧单文件。
- `CopyQueue`：`sessionEnding` 改为按会话的集合，只停属于该会话的拷贝；同一时间仍只跑一个拷贝任务（保持简单）。
- `AutoMount`：准入从“没有任何写会话”改为“这块盘没有会话且会话数未到上限”；自动尝试仍串行。
- 应用更新（`AppUpdates.swift:64-72`）：逐个结束所有会话。
- 诊断：`lastOperation` 改为列表，诊断格式升到第 5 版。

### 阶段 4：App 界面
- 删除 `writeHolder`/`WriteSlotWait`；达到上限时改为“已有 2 块盘在读写”。
- 底部栏按盘列出读写中的盘，“恢复只读”放进各盘详情。
- 推出、抹掉、高级菜单、`clearCheckMarker`/`writeAfterRecovery`、拷贝目标都按盘取会话。
- 菜单栏、错误文案、本地化（中英繁）同步；官网兼容表“同时读写多块磁盘：暂不支持”改掉（历史更新日志不动）。

### 阶段 5：验收
- 单元/集成：现有写死单盘规则的测试改为新语义（`DiskReadinessTests`、`AutoMountTests` 第二块盘排队、`HelperWriteLifecycleTests`、`MountCycleClientTests` 的 `blocksActions` 断言、`CopyQueueTests` 会话结束语义）；新增两会话交错的启动、恢复、拔线、更新用例。
- 扩展故障矩阵：两个卷并行各跑一遍，加“两块同时拔”“一块拔一块继续写”。
- 实盘（需要第二块 NTFS 盘）：两块同时拷贝；拷贝中拔 A，B 不受影响且完整；两块都拔再插回各自恢复；读写中升级 App；重启后两块都恢复；克隆盘被拒绝。
- macOS 15 虚拟机回归。

## 四、风险与原则

- 阶段 2、3 动的是拔线恢复链路，是全项目风险最高的部分：每一步保持单盘路径行为不变、测试全绿后再进下一步。
- 升级兼容：新 helper 要能接管旧版留下的 `operation.json` 与旧 intent 文件；扩展声明（EXAppExtensionAttributes）与各组件权限不得改变。
- 没有两块实体盘实测，不对外宣称支持。

## 五、建议顺序

1. 拷完精确确认（第二节）+ 第二块盘转圈修复（`8241240`）→ 0.8.4。
2. 阶段 1 → 2 → 3 → 4，逐阶段提交；拿到第二块 NTFS 盘后做阶段 5，通过后作为 0.9.0 发布。
